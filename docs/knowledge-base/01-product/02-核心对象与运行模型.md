# 核心对象与运行模型

> 这一篇回答一个问题：**MALING 内部到底在管哪些东西？**
> 看懂这些对象，后面所有的界面、状态、恢复、产物都变得可解释。

## 1. 对象总览

```text
workspace（工作空间 / 项目）
　└─ task（一次需求）
　　　├─ scheduled-task（定时任务定义，可选触发源）
　　　└─ run（一次执行）
　　　　　└─ round（一轮循环）
　　　　　　　└─ node（工作流节点）
　　　　　　　　└─ attempt（节点的一次执行）
　　　　　　　　　　├─ ACP session（与 Agent 的会话）
　　　　　　　　　　├─ artifact（规范化产物）
　　　　　　　　　　└─ attachment（附件）
```

| 对象 | 是什么 | 谁创建 |
| --- | --- | --- |
| **workspace** | 你添加进侧边栏的项目目录，有独立 id 与独立运行数据 | 用户 |
| **task** | 一条需求 / 一次会话的顶层容器，标题即自动生成的会话标题 | 用户发起会话时 |
| **run** | task 下的一次执行；同一需求再跑一次就是新 run | runtime |
| **round** | run 内的一轮；工作流走到 `$new-round` 就开新 round | runtime |
| **node** | 工作流里的一个节点（一次 Agent 执行 + 结果判定） | 工作流 DSL |
| **attempt** | 某个节点的一次执行；**每次执行都新建，绝不复用** | runtime |
| **artifact** | runtime 规范化落盘的产物（可被后续节点读取） | runtime |
| **scheduled-task** | 定时器定义，到点触发上面这条链 | 用户 |

## 2. 三条最容易被误解的规则

### 2.1 顶层对象是 task，不是 conversation

- 新需求 = 新 task
- 同一需求的再次执行 = **同一 task 下的新 run**
- 同一 run 中的验收新一轮 = **新 round**
- 同一 round 中某个节点的一次执行 = **一个 attempt**

所以你会看到 `task-001 / run-001 / round-001 / dev / attempt-001` 这样的层级，而不是「一个会话文件夹里塞满所有东西」。

### 2.2 session 可以复用，attempt 目录绝不复用

- **session 复用**：可以让新节点接着上一轮的上下文继续说（边的 `session=continue`，或 Direct 的追问）。
- **attempt 不复用**：每次执行都新建 `attempt-NNN`，任何一次执行都不会覆盖上一次的产物。

这条规则保证了"历史可追溯"——你永远能看到某次执行当时代码、日志、产物到底是什么样。

### 2.3 runtime 只信规范化产物，不信模型自己起的文件名

- canonical artifact 必须由 runtime 规范化落盘。
- 模型自由创建的文件只能算 side effect 或 attachment。
- 后续节点通过 runtime registry 拿产物，**不去猜路径**。

## 3. status 与 outcome 必须分开看

这是排障时最重要的一组概念：

| 字段 | 含义 | 取值 |
| --- | --- | --- |
| `status` | **生命周期**：还在跑、挂起、结束了 | `running / paused / completed` |
| `outcome` | **终局结果**：结束得怎么样 | node: `success / failure / invalid / killed / null`<br>run / round: `success / failure / killed / null` |

统一约束：

- `status != completed` 时，`outcome = null`；
- `status = completed` 时，`outcome` 必须是终局值；
- **`paused` 只属于 status，不属于 outcome**（挂起不是结果）；
- `failure` = 目标未达成或执行失败；
- `invalid` = 结果不满足最小契约（**runtime 内部状态，不会作为边的走向依据**）。

## 4. 一个节点是怎么被判定成功的

节点 outcome 有三条来源路径：

```text
路径 1  provider 成功且无产物要求
        → success

路径 2  AI 输出验证（声明 output + success_condition）
        → 读 artifact → 按条件求值
        → success / failure
        → 若声明了 output.schema 且输出不合法 → 内部 invalid → 自动隐藏追问修复

路径 3  人工 check（manual_check=true）
        → 会话结束暂停 → 用户点「成功」或「失败」
```

注意：
- **provider 异常（鉴权、额度、限流、模型不可用、传输、IO）不算 failure**，会被归一化成 `RuntimeErrorInfo`，映射到 `runtime-abnormal` 或 `error-blocked`，不会驱动 failure 边。
- `manual_check` 与 AI 输出验证**互斥**，同一节点不能既要求 AI 判分又要求人工判定。

## 5. 工作流 DSL 速览

工作流是一份 JSON：**节点 + 边 + 控制规则**。

```json
{
  "version": "0.1",
  "id": "dev-test-accept",
  "entry": "dev",
  "control": { "max_attempts": 3, "max_rounds": 2 },
  "nodes": [
    { "id": "dev", "type": "worker", "provider": "claude-acp",
      "profile": "pf-example-developer", "goal": "实现需求" },
    { "id": "test", "type": "worker", "provider": "claude-acp",
      "goal": "检查实现并输出 JSON 结果",
      "output": { "kind": "json", "artifact": "test-result",
                  "schema": { "reason": "String", "result": "boolean" } },
      "success_condition": { "expression": "$.result == true" } },
    { "id": "accept", "type": "worker", "provider": "claude-acp",
      "goal": "对照需求判断是否满足验收条件", "manual_check": true }
  ],
  "edges": [
    { "from": "dev", "to": "test", "on": "success" },
    { "from": "test", "to": "accept", "on": "success" },
    { "from": "test", "to": "dev", "on": "failure", "session": "continue" },
    { "from": "accept", "to": "$new-round", "on": "failure" },
    { "from": "accept", "to": "$end", "on": "success" }
  ]
}
```

关键约束：

- `version` 首版固定 `0.1`。
- 必须至少有一条指向 `$end` 的边；`$end` 只能作边目标，不能作节点 id。
- 边的 `on` 只接受 `success` / `failure`。
- **同一节点的同一结果类型只能有一条出边**（一个节点只能有一条 success 边）。
- `session=continue` 只能指向真实 worker 节点，且该 provider 必须支持 continue。
- `manual_check=true` 与 AI 输出验证互斥；`success_condition` 必须搭配 JSON `output`。
- `control.max_attempts` 只统计**失败触发的回退**；`max_rounds` 只统计 `$new-round` 开出的一轮。
- `output.schema` 不合法触发的自动隐藏修复**不消耗** attempt 次数。

### 5.1 两种节点

| 节点类型 | 用途 | 说明 |
| --- | --- | --- |
| `worker` | 通用 AI 执行节点 | 由 `provider` + `profile`（角色）+ `goal` + `output` 共同决定行为 |
| `ai-dynamic` | 复合动态编排节点 | 内部有自己的动态图：fanout、merge、acceptance；内部节点不污染外层 round |

## 6. AI-DYNAMIC（AUTO 的底座）

`ai-dynamic` 是"工作流里的一个节点，但它自己又是一个小调度器"：

- 外层 runtime 按固定 DSL 前进；
- 进入该节点后，内部根据 `dynamic-node-completion` 产物派生后续内部节点；
- 可以 fan-out 到多个子任务（各自跑在独立 Git worktree 里），然后 merge、acceptance；
- 动态控制限制：`maxDynamicNodes` / `maxFanout` / `maxDepth` / `maxParallel` / `maxGroupDepth` / `maxWorkflowInvocations`。

**边界很重要**：Agent 只能"提议"下一步，runtime 校验并持有真实状态，Agent 不能直接改 runtime。

## 7. 目录解析优先级

| 解析对象 | 优先级（从高到低） |
| --- | --- |
| workflow | CLI 参数 `--workflow` → task 目录默认 workflow → 项目预设 → 用户预设 |
| provider | 节点显式声明的 `provider` → runtime 默认 provider |
| profile（角色） | 客户端内建 profile → 用户目录 profile |

约束：节点声明了 `profile` 却在 run start 时解析不到，**直接失败**，不做静默兜底。
