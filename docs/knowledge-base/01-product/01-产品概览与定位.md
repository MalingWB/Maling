# 产品概览与定位

## 1. 一句话定位

**MALING 是一个本地优先的开源 AI Agent 桌面客户端。** 它通过 ACP 把 Claude Code、Codex 等 Coding Agent 接进同一个桌面工作区，并在它们之上提供工程化的任务编排、执行观测与产物审阅能力。

> **命名说明**：本产品原名为 **Gold Band**，现统一更名为 **MALING**。名字承自"金箍"的寓意——能力强大的东西（Coding Agent）需要恰当的约束，才能发挥出更强的能力。MALING 就是套在 Agent 外面的那道「约束」，用程序化的手段严格控制工作状态的流转与循环。
>
> 更名只涉及产品名称。文档里出现的路径、目录、环境变量、CLI 命令、主题名等**实现标识仍沿用原命名**（如 `~/.gold-band/`、`GOLD_BAND_HOME`、`gold-band run`、内置主题「Gold Band」），它们不是产品名，请勿等价替换。

## 2. 它明确不是哪些东西

理解定位最快的办法，是先排除误解：

| MALING 不是 | 原因 |
| --- | --- |
| CLI / TUI 的图形皮肤 | 它有独立的桌面产品心智，主路径是菜单、按钮、抽屉、设置页，不保留命令行入口 |
| 单纯的聊天应用 | 会话只是入口，真正的价值在运行、校验、恢复与产物审阅 |
| 终端模拟器 | 不提供终端面板，Git 操作通过图形化源码管理完成 |
| 单页大仪表盘 | 首页是工作台（会话 + 列表），不是 KPI 看板 |
| 又一个 Agent 框架 | 它不替换 Agent，而是在 Agent 之上做编排；节点内部仍然是你熟悉的 Claude Code / Codex |

## 3. 它解决的问题

### 3.1 控制流依赖模型上下文，容易漂移

如果"下一步做什么"由模型在上下文里自行决定，长任务一旦上下文被压缩、被打断、被无关信息污染，流程就会走偏。

MALING 的做法：**控制面 deterministic，执行面 probabilistic**。DSL 定义节点与边，runtime 根据节点的 canonical outcome 决定下一步；模型只负责"在当前节点里把活干好"。

### 3.2 子执行单元难以复用已有生态

一个纯 prompt 层的编排只能改"说什么"，不能改"谁来干"。MALING 的节点可以声明**不同的 Agent**：验收节点用带浏览器能力的 Codex，开发节点用轻量的 Pi，都是合法的。

### 3.3 "是否完成"不能只靠 Agent 自报

Agent 说"已完成"不等于交付达标。MALING 把完成判定拆成三种可验证路径：

1. **provider 成功**（无产物要求时）；
2. **AI 输出验证**：节点声明 `output` + `success_condition`，runtime 读取产物按条件求值；
3. **人工 check**：会话结束暂停，由用户判定成功 / 失败。

## 4. 核心设计原则

### 4.1 provider-first / ACP-first

- 核心抽象是 **provider**，不是某个具体 Agent。
- provider 的输出统一走 ACP，会话详情基于 ACP session events 可视化，不再为每个 Agent 维护一套私有可视化协议。
- 新增能力优先选择 ACP-compatible adapter，而不是给某个 Agent 打补丁。

### 4.2 runtime 控制流外置

- 控制面（谁先谁后、失败怎么办）由 runtime 决定。
- 执行面（这个节点里怎么写代码）交给 Agent。
- 完成判断基于 artifact 与验证，而不是 self-report。

### 4.3 desktop-first，运行事实由 runtime 统一管理

- 桌面客户端是主产品入口；CLI 保留为脚本化 / CI 入口，不再是主交互心智。
- Rust runtime / storage / DSL / provider adapter 是 canonical backend contract。
- 前端必须复用 runtime 契约，**不得**从日志或 provider 输出重新推断终局状态。

### 4.4 会话为入口，可视化管理工程流程

- 用户在会话输入区描述目标，用 Direct / Workflow / AUTO 选择执行方式。
- 工作区管理、配置与审阅使用菜单、按钮、工作流画布、右侧工作区和设置页。
- 会话内容用于交流；运行、停止、继续与终态仍服从统一的 runtime / lifecycle 契约。

## 5. 三种运行模式（先建立印象）

| 模式 | 心智 | 适合场景 | 详细说明 |
| --- | --- | --- | --- |
| **Direct** | 和某一个 Agent 持续对话 | 日常提问、改代码、调试 | [运行模式指南](../02-practice/02-运行模式指南.md) |
| **Workflow** | 执行一份固定的工作流 | 有清晰阶段、需要独立评审与失败回退 | 同上 |
| **AUTO** | AI 动态拆分并调度子任务 | 大到无法事先画出完整流程图的需求 | 同上 |

## 6. 主流程一览

```text
选择工作空间 / Agent / 执行方式
        ↓
发起会话或运行工作流
        ↓
观察会话、工具调用、运行状态；必要时人工介入
        ↓
在右侧工作区审阅文件、Markdown、Diff
        ↓
确认结果 → 源码管理里提交
```

## 7. 平台、语言与形态

- **平台**：Windows（主要目标）、macOS（Apple Silicon / Intel）、Linux（未完全验证）。
- **界面语言**：简体中文、繁體中文、English、日本語、한국어、Português (Brasil)、Español（七种，界面语言包无英文兜底，缺词视为构建缺陷）。
- **技术栈**：Tauri 2 + Rust（后端）/ React + TypeScript + Tailwind + shadcn/ui（前端）。安装包只有几十 MB，多会话并行时内存约 300 MB 量级。

## 8. 什么时候它适合你

**适合**：
- 想用**一个**桌面客户端管多个本地 Coding Agent；
- 需要持续对话、历史恢复、附件协作的开发任务；
- 需要把开发 / 评审 / 测试 / 验收分开的长任务；
- 需要过程记录、产物留档、失败可恢复的任务。

**暂时不适合**：
- 要求稳定商业 SLA 的生产环境；
- 完全依赖尚未支持的 ACP / Provider 特性的负载；
- 需要图形终端或移动端远程操控的场景（尚未提供）。
