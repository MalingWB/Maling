# 架构与扩展点

> 给要改代码、加功能的人。看完能说清：代码分几层、数据契约在哪、想加东西该动哪里。

## 1. 分层

```text
┌─────────────────────────────────────────────────────────┐
│ web/           React + Tailwind + shadcn/ui              │
│                只负责应用壳、页面栈、图形展示与直接操作     │
└──────────────────────┬──────────────────────────────────┘
                       │ Tauri commands（交换 ViewModel）
┌──────────────────────▼──────────────────────────────────┐
│ src-tauri/      桌面壳：窗口、托盘、通知、IM、定时器调度    │
│                 通过 path dependency 复用 core 的 App      │
└──────────────────────┬──────────────────────────────────┘
                       │ Rust API（canonical contract）
┌──────────────────────▼──────────────────────────────────┐
│ src/            Rust core：runtime / storage / DSL /     │
│                 provider adapter / artifact / layout     │
└──────────────────────┬──────────────────────────────────┘
                       │ ACP（JSON-RPC over stdio）
┌──────────────────────▼──────────────────────────────────┐
│ ACP adapters    claude-acp / codex-acp / 其它 Agent       │
└─────────────────────────────────────────────────────────┘
```

**铁律**：前端不得从日志 / provider 输出反推终局状态；一切以 runtime 的 canonical state 为准。

## 5. 提示词管理（强约束）

- 所有内置提示词（profile、runtime、repair、AI-DYNAMIC 等）必须放在 `src/prompts/` 下，**不允许**散落在实现代码里。
- 语言目录：`zh-CN / zh-TW / en / ja-JP / ko-KR / pt-BR / es`，各语言相对路径必须一致；角色缺某语言时降级到英文。
- 例外：CI/CD 角色正文、`runtime/cicd-goal.md`、远程任务运行时提示词只保留简体中文与英文。
- **system prompt vs user prompt 的区分标准**：
  - 由 runtime 决定、用户不操心、需稳定执行 → system（角色、历史、目录、文件规则、能力边界、预算、输出协议、repair 指令）；
  - 与本次目标直接相关、随任务变化 → user（requirement、goal、当前 task）。
- 修改提示词正文前必须读 `docs/gold-band/rules/prompt-authoring.md`。

## 6. 前端约定

| 主题 | 约定 |
| --- | --- |
| 组件 | 优先 shadcn/ui + Tailwind utilities；基础控件用 copy-in 生成再改，不自研消息容器 / 输入框 / 工具卡片 / Markdown 渲染 |
| AI chat UI | 优先 prompt-kit copy-in 组件 |
| 文案 | 全部走 `web/src/locales/`，七语言 key 集合必须一致（CI 校验）；缺词视为构建缺陷 |
| 错误 | 后端只给 code + params；前端按 code 本地化，后端不含对客文案 |
| 主题 | 业务组件只消费语义 role（`composer`、`message-assistant`、`activity`…），**不得**读 `themeId` 分支 |
| 性能 | 先找数据量 / 刷新范围 / 状态边界根因，不用零散 `memo` 掩盖；详见 `rules/frontend-performance.md` |
| 数据加载 | 按数据规模拆分接口、渐进加载；详见 `rules/data-loading.md` |

## 7. CLI 入口

```bash
# 执行一次需求（AUTO 或指定工作流二选一）
gold-band run \
  --requirement-file requirement.md \
  (--auto-config auto.json | --workflow workflow.json)

# 继续一个暂停的 run
gold-band continue --task-id <task_id> --run-id <run_id> [--recover-interrupted]
```

| 退出码 | 含义 |
| --- | --- |
| 0 | run 完成且 outcome = success |
| 1 | run 完成但 outcome 非 success |
| 2 | run 暂停 |
| 3 | 命令失败（参数 / 配置 / Git preflight / 创建 run） |
| 4 | 返回时仍 running（防御性） |

无人值守语义：追问自动 `decline`，权限自动 `cancelled`，暂停类节点保持暂停。CLI 与桌面共用同一个 `create_conversation_run`，所以 CLI 创建的任务能在桌面里打开并继续。

## 8. 本地开发

```bash
npm install
npm run dev          # 热加载开发
npm run dev:static   # 固定源码快照，不随修改热加载

cargo check
npm run web:test
npm run web:build
```

- 包管理器统一 `npm`，锁文件以根 `package-lock.json` 为准。
- 文档编辑不会触发 Rust 重建（`.taurignore` 排除 `docs/`）。

## 10. 发布渠道与产品命名

| 渠道 | 产品名 | 更新源 | 说明 |
| --- | --- | --- | --- |
| `default`（开源渠道） | Gold Band | 上游 GitHub Release | 不带 metrics、不带用户反馈 |
| `wb`（企业渠道） | **MALING** | 内网更新地址 | 带 metrics、用户反馈、渠道身份 |

- **产品已从 Gold Band 更名为 MALING**。当前面向企业的正式产品名是 **MALING**（`wb` 渠道）；`default` 渠道作为开源渠道继续沿用 Gold Band 名称。
- 更名只改变产品名称与品牌展示，**不改变**实现标识：数据目录 `~/.gold-band/`、环境变量 `GOLD_BAND_HOME`、CLI 命令 `gold-band`、Rust crate 名、内置主题名「Gold Band」等均保持原样。
- 因此两台渠道可以共存在同一台机器上：它们各自的标识符（`local.gold-band.desktop` / `local.maling.desktop`）与主程序文件名不同。

- 渠道配置在 `configs/channels/*.json`；构建通过 overlay 生成。
- 每个渠道有独立主程序文件名（`gold-band-desktop.exe` / `maling-desktop.exe`），装一个不会关掉另一个。
- GitHub Release 统一构建四平台（Windows x64 / Linux x64 / macOS Intel / Apple Silicon），产出七语言 manifest + `latest.json`。
