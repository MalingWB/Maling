# 运行模式指南

> Direct / Workflow / AUTO 是 MALING 的三种执行方式。它们的差别不是"聊天风格"，而是**谁在决定下一步**。

## 0. 一张表看懂区别

| | Direct | 工作流（Workflow） | AUTO（AI-DYNAMIC） |
| --- | --- | --- | --- |
| 谁来定下一步 | 你 | 工作流 DSL | AI 提议 + runtime 校验 |
| 是否有角色 / 节点 | 无 | 有，显式画布 | 有，运行时由 AI 生成 |
| Agent 数量 | 1 个 | 每节点可不同 | 控制面 + 若干 worker |
| 完成判定 | 无（对话本身即结果） | provider / AI 输出验证 / 人工 check | 内部 acceptance + 外层流程 |
| 隔离方式 | 当前工作位置 | 可每 run 独立 worktree | 每个子任务独立 worktree |
| 典型耗时与 token | 最低 | 较高 | 最高 |
| 适合 | 提问、改代码、调试 | 有清晰阶段的长任务 | 大到画不出流程的需求 |

> 三种模式**各自保留自己的配置**，切换模式不会清空正文和附件。

---

## 1. Direct

### 1.1 行为

- MALING **不注入任何工作流 system prompt**，只提供统一的桌面 UI、会话存储、附件、模型与权限配置、停止与恢复、token 与耗时统计。
- 一轮对话 = 一个 ACP turn。底层仍有一个 run 容器，但后续追问复用同一 ACP session，不会每次开新 run。
- 停止只取消当前回复；之后输入的任何内容都走普通 ACP prompt，不会推进"工作流"。

### 1.2 配置在 composer 内闭环

| 配置 | 位置 | 记忆范围 |
| --- | --- | --- |
| Agent | 底部 Agent 图标列表 | 上次选择 |
| 模型 | 右下角「模型」 | `工作空间 + Agent` |
| 思考强度 / 模型配置 | 随模型切换 | 按 `(Agent, 模型)` 分别记忆 |
| 权限模式 + Auto Accept | 右下角「权限」 | `工作空间 + Agent` |

要点：

- 所有配置都可选「不指定」——不干预 Agent 当前配置。
- **会话创建后不能换 Agent**；换 Agent 等价于新建会话。
- 会话内改模型 / 权限只作用于本会话，不写回主页记忆。
- 如果某个配置项当前 Agent 不支持，系统会自动回滚为「不指定」并在消息流里用分隔线提示（带具体配置项名）。

### 1.3 后台与常驻

- Direct 会话是"存活会话"：一轮结束后仍会接收并持久化 Agent 的后续消息。
- 空闲会自动回收（默认空闲 10 分钟、最多 8 个空闲会话），按最近活动 LRU 淘汰。
- 需要长期挂着（例如配套定时任务）时开启**常驻会话**：会话右键「常驻会话」，或会话头部的图钉按钮。

### 1.4 什么时候别用 Direct

- 你希望"先实现 → 再独立评审 → 再测试 → 出问题自动回退"——用工作流。
- 你希望"自动拆成若干并行子任务再合并"——用 AUTO。

## 2. 工作流（Workflow）

### 2.1 行为

- 一次 run 按一份工作流 DSL 执行：节点 = 一次 Agent 执行，边 = 结果（success / failure）决定去向。
- 每个节点可以有自己的 Agent、模型、角色、输出协议、结果判定方式与权限。
- run 启动时会**冻结工作流快照**（`workflow.snapshot.json`）；之后改模板不影响已开始的 run。

### 2.2 编辑工作流

入口：会话 composer 选「工作流」→ 选模板；或在「运行模式」页管理工作流模板；或会话页顶部「工作流」卡片（查看 / 修改 / 修复）。

画布能力要点：

- `+` 菜单可加：Agent 节点、AI-DYNAMIC 节点（能力开启时）、结束节点、New Round 节点。
- 每个真实节点有 success 出线；开了 AI 输出验证或人工 check 的节点额外有 failure 出线（上下对称）。
- **入口自动派生**：没有初始入边的节点显示「入口」，唯一候选自动写入 `entry`；零个或多个候选都不能保存。
- 布局自动整形（ELK layered），坐标不写进 DSL；节点顺序以 success 主链为准，failure 边按分支路由。
- 选中节点时右侧 Inspector 分三块：**模型配置 → 工作流控制 → 节点配置**。
- 支持 `Ctrl/Cmd+Z` 撤销、`Ctrl/Cmd+Y`（或 `Ctrl/Cmd+Shift+Z`）重做，保留最近 50 步。
- 保存前持续校验，Inspector 顶部有问题摘要，点问题可定位节点/边。

### 2.3 结果判定三选一

| 方式 | 配置 | 界面表现 |
| --- | --- | --- |
| provider 成功即成功 | 不配 `output` | 最简单，适合"能跑完就算过" |
| AI 输出验证 | `output`（JSON）+ `success_condition` | 需要模型输出结构化 JSON，runtime 按表达式求值 |
| 人工 check | `manual_check: true` | 会话结束暂停，等你在 composer 上点「成功」/「失败」 |

> `manual_check` 与 AI 输出验证互斥。声明了 `output.schema` 但输出不合法时，runtime 会自动在同一会话里做**隐藏修复**（最多 3 次），不消耗 attempt 次数。

### 2.4 失败与循环

- `max_attempts`：同一个 round 内，由 `failure` 触发的回退次数上限，默认不限制。
- `max_rounds`：`$new-round` 开出的轮次上限。
- `session=continue` 的失败边可以让下一节点**接着出问题的会话继续**（"回去修"），而不是开新会话。

### 2.5 什么时候别用工作流

- 需求边界还不清楚、你也不知道该分几步——先用 Direct 聊清楚，再固化工作流，或直接上 AUTO。

## 3. AUTO（AI-DYNAMIC）

### 3.1 行为

AUTO 本质上是一个**只有 AI-DYNAMIC 节点的工作流**：

1. **bootstrap**：控制面 Agent 读需求，产出 `dynamic-node-completion` 提议（下一步做什么、拆成哪些子任务）。
2. **runtime 校验提议**：合法才物化，不合法就隐藏修复 / 暂停。Agent 不能直接改 runtime。
3. **并行执行**：每个子任务在自己的 Git worktree 里跑（默认最多并发数受 `maxParallel` 限制），彼此不干扰。
4. **merge**：合并结果。
5. **acceptance**：判定这一轮是否达标。
6. **决策下一轮**：不达标则再派发一轮，直到达标或用尽限制。

### 3.2 两种 Agent 策略

| 策略 | 说明 | composer 里能看到 |
| --- | --- | --- |
| **固定 Agent** | 所有内部分发都用同一个 Agent | Agent、模型、权限（+ Auto Accept） |
| **动态 Agent** | 每个 worker 可以选不同 Agent，各自预设模型 / 权限 / 思考强度 | 只显示「Dynamic Agent」标识 |

两种策略都支持一个非必填的**全局 Goal**：会追加到每个内部节点的目标上。

### 3.3 动态控制限制

| 限制 | 含义 |
| --- | --- |
| `maxDynamicNodes` | 一次 run 最多派生多少个内部节点 |
| `maxFanout` | 一次 fan-out 最多并行多少个 |
| `maxDepth` | 最大嵌套深度 |
| `maxParallel` | 最大同时执行的节点数 |
| `maxGroupDepth` | 多层 fan-out 的最大组深度 |
| `maxWorkflowInvocations` | 最多调用多少次已注册工作流 |

还可以限制 `allowedWorkflows`（只允许调用哪些已注册工作流），以及 `allowNestedDynamic: false` 禁止嵌套 AI-DYNAMIC。

### 3.4 AUTO 的成本现实

AUTO 的「提议 → 校验 → 并行 → 合并 → 验收 → 再来一轮」是**对抗式验证 + 循环**，所以它比直接问 Agent 慢、也更费 token。换来的是更少的返工与更可控的终局。

### 3.5 什么时候别用 AUTO

- 任务小、目标明确：直接 Direct 更快。
- 你已经知道该分几步：画成工作流比让 AI 现场编排更稳定、更可预测。

## 4. 通用：三种模式共享的行为

### 4.1 工作位置

composer 顶部信息栏可选**工作位置**：

- **主工作区**：直接在项目目录干活。
- **新工作树 / New worktree**：从当前分支 `HEAD` 派生一个独立 worktree，适合并行不互相干扰。

要点：
- 选择 worktree 后，发送时会把当时的 `HEAD` 固化为本次 run 的 fork 点；发送前继续在同一分支 commit 是安全的。
- 如果发送前工作目录已经切到别的分支，会结构化失败（`git.ref-changed`），不会偷偷从新分支派发。
- 非 Git 工作空间也显示「新工作树」，但选择时会先做 Git 能力预检并给出明确错误。

### 4.2 待发送队列

运行中继续输入会进入「待发送」队列，按顺序被消费。可以编辑、删除队列项，数量有上限。

### 4.3 状态点语义

侧边栏会话行：

- **Direct**：显示 Agent 图标；有活跃回合时图标轻微呼吸。不显示成功 / 失败色点。
- **Workflow / AUTO**：显示状态点——绿（成功）/ 红（失败 / 异常 / 停止）/ 黄（暂停）；运行中不显示时间。

### 4.4 运行模式的记忆范围

- 运行模式选择按 **工作空间** 记忆；切换工作空间会加载该空间上次的模式。
- 工作流模板与 AUTO 模板在「运行模式」页按项目维护。
- 「下一次 Run」的 AUTO / 工作流配置属于**任务**（`authoring/auto.json`、`authoring/workflow.json`），改它不会改项目默认。

## 5. 选型速查

```text
问题是"我需要它帮我想 / 改 / 查一下"？
    → Direct

问题是"我知道该怎么做，但要它按步骤做，还在关键点把关"？
    → 工作流

问题是"我大概知道要什么，但拆解和排期我不想自己定"？
    → AUTO（并接受更高的耗时与 token）

需求本身还没想清楚？
    → 先 Direct 聊清楚，再决定固化
```
