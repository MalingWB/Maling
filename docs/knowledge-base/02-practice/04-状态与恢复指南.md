# 状态与恢复指南

> 任务跑到一半停了、卡住了、报错了，先来这里。
> 核心思路：**先看 run 的 status 与 outcome，再看 pause reason，最后才决定点哪个按钮。**

## 1. 先看两个字段

| 字段 | 你可能看到 | 含义 |
| --- | --- | --- |
| `status` | `running` | 正在跑 |
| | `paused` | 挂起了，等你介入或需要恢复 |
| | `completed` | 已结束（这时才看 outcome） |
| `outcome` | `success` | 达成目标 |
| | `failure` | 目标未达成 / 执行失败 |
| | `invalid` | 结果不满足最小契约（内部态，不驱动边） |
| | `killed` | 被终止 |
| | `null` | 还没结束 |

**`paused` 只属于 status，它不是结果。** 看到 `paused` 时要继续看 pause reason。

## 2. 暂停原因与对应动作

| pause reason | 界面文案 | 该点哪个按钮 |
| --- | --- | --- |
| `process-interrupted` | 进程已中断 | **继续工作流** |
| `runtime-abnormal` | 运行异常，可继续处理 | **继续工作流**（可附带修复指令） |
| `error-blocked` | 因错误阻塞，处理后可继续 | 先修阻断原因（配置 / 文件等），再继续 |
| `waiting-for-user-input` | 等待用户输入 | 在追问卡片里回答 |
| `permission-requested` | 等待权限决策 | 在权限卡里 Allow / Reject |
| `manual_check_pending` | 等待人工判定 | 点「成功」或「失败」 |

> 「等待用户输入」「等待权限」「人工 check」「错误阻塞」这些是**结构化干预态**，不能用通用「继续工作流」绕过它们。

## 3. 三个容易混淆的按钮

| 按钮 | 什么时候出现 | 做了什么 |
| --- | --- | --- |
| **继续工作流** | 当前节点还没完成，run 因中断 / 异常暂停 | 恢复当前 attempt 与 ACP 会话的 runtime 控制，让它继续干原来那件事 |
| **恢复工作流** | 当前节点**已完成且成功**，但节点完成到下一次跳转之间中断了 | 直接用已持久化的完成结果做下一步决策，**不会**重新调用当前节点的 Agent |
| **继续并发送** | 你有输入，同时又需要恢复 | 把"你的新输入 + 恢复意图"原子提交，不会先普通发送再 continue |

另外两个：

- **重跑该任务**：用同一需求开一个新 run（历史 run 保留）。当前 run 还在跑会先停止。
- **继续（普通消息）**：停止后的 composer 是普通输入框，发送只走普通 ACP prompt，**不会**推进工作流。

## 4. 停止之后到底发生了什么

```text
你点「停止」
    ↓
当前 ACP 回合被取消
    ↓
Workflow / AUTO：run 进入 Paused + ProcessInterrupted，可显式继续
Direct：只取消这一轮回复，composer 保持普通输入，不出现"继续工作流"
```

重要细节：

- **Workflow/AUTO**：停止后输入框仍可用，但发送的消息是 `NonRuntimeControlled`——可以有问有答，但不会提取产物、不会判定结果、不会推进节点。想继续干活必须点「继续工作流」。
- **Direct**：停止只是取消当前回复，之后任何输入都是普通对话。
- 停止后新到达的权限 / 追问请求会被结算为 `cancelled`，不会长期挂着。

## 5. 恢复时的几个坑

### 5.1 已进入"产物归一化"阶段怎么办

工作流节点分两阶段：先跑业务回合，再由 runtime 发一个隐藏回合把结果归一化成 canonical artifact。

| 情况 | 恢复行为 |
| --- | --- |
| 业务回合没跑完就中断 | 继续恢复**业务对话**，不假设任务已完成 |
| 已进入产物归一化阶段，纯继续 | 只恢复隐藏的归一化回合，**不会重跑已完成的业务工作** |
| 已进入归一化阶段，但你"继续并发送" | 新输入作为新的业务回合完整执行，完成后再重新归一化 |

所以：不确定跑到哪了，看 run 的 attempt 状态和产物，不要盲目重跑。

### 5.2 产物输出不合法

- runtime 会在同一会话里自动做隐藏修复，**最多 3 次**。
- 3 次仍不合法 → 收敛为 `Paused + RuntimeAbnormal`，错误码 `workflow.output.repair-exhausted`（带节点、attempt、修复次数参数）。
- 此时输入框可以普通输入，补充修复指令后继续当前 attempt 即可。

### 5.3 AI-DYNAMIC 暂停

- AI-DYNAMIC 内部每个暂停的节点都会在自己的 ACP 会话里恢复，等同于逐个点「继续」。
- 同一 AI-DYNAMIC attempt 只有一个调度 driver，其余交给它。
- 没有暂停的内部节点时，走 run 级 continue。

### 5.4 双击 / 重复点击继续

- 恢复请求带 revision，并在 attempt 短锁 + per-run lease 内校验，重复请求不会重复推进。
- 启动握手有 60 秒上限：超时返回 `runtime.continue-launch-timeout` 并回落到可恢复暂停，可以重新点。

## 6. 常见失败场景速查

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 一直显示加载、没有输出 | Agent 无响应 / 上下文压缩中 / adapter 排队 | 看原始帧是否有 `acp_rpc_begin` 无 `end`；压缩中会显示「正在压缩上下文」（超 120 秒会提示耗时较长） |
| 权限请求点了没反应 | 卡片已过期 / 已在另一端处理 | 看是否显示"已由其他端处理"；刷新会话 |
| 消息停留在"等待人工判定" | `manual_check` 节点 | 点「成功」或「失败」 |
| "当前 Agent 暂不支持配置：xxx，已回滚为不指定" | 切换模型后原配置项不被新模型支持 | 正常行为；需要时停止对话后重新选择 |
| 附件发送失败，提示路径过长 | 数据目录层级过深 + 文件名过长 | 新建会话后重新发送 |
| 无法创建新工作树 | Git 状态 / 分支冲突 | 检查是否有 merge/rebase 进行中、目标分支是否被其他 worktree 占用 |
| Workflow/AUTO 发送后没推进 | 停止后发的普通消息不推进流程 | 点「继续工作流」或「恢复工作流」 |
| OAuth / 鉴权失败 | Provider `AuthRequired` | 到对应 Agent 完成登录后**手动重新发送**（不会自动重发） |

## 7. 恢复能力边界（不要指望这些）

- **Direct 没有"继续工作流"**：它不受 runtime 编排，停止即取消当前回复。
- **历史 attempt 不能继承继续动作**：继续只属于 run 当前的 attempt / leaf。
- **`ErrorBlocked` 不能靠继续绕过**：必须先解决阻断原因。
- **模型配置过期不会自动重试**：会被规范化为"不指定"并用 provider 默认模型继续，这在生命周期里会记录 `model_config_normalized` 事件。
