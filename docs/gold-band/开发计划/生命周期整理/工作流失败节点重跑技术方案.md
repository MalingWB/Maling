# Workflow 失败节点重跑技术方案

日期：2026-11-12。状态：已实施，定向验收完成。

## 1. 需求与根因

支持普通 Worker 的已完成失败 attempt、已结束 Run 的失败节点、历史失败 attempt。`ErrorBlocked` 暂不支持；Direct、AUTO 和 AI-DYNAMIC 内部节点不扩展。现有 RuntimeAbnormal 当前节点重试继续使用原 Run 的新 attempt。

现有按钮缺失源于当前重试契约只覆盖 canonical current attempt 的异常暂停，并非单纯 UI 判断错误。Completed Run 不允许复活。新增操作必须建立独立 successor Run、冻结输入前缀和清晰的会话写边界。

## 2. 复用与方案取舍

采用历史分叉、新执行身份和新会话这一工作流 reset 常见模式，复用现有执行计划、原子 JSON、Run/attempt 目录预留、dispatch 锁、运行代际 fencing、后台 driver 和启动恢复候选；不引入新的工作流引擎或依赖。

本方案取代《工作流节点Attempt重跑与Run封存迁移方案》中与本期失败节点重跑重叠的设计。暂不迁移旧 ACP session 的 continuation ownership，不复制完整聊天、Raw 日志，不增加 Superseded 生命周期、lease registry 或多阶段 handoff 状态机。历史聊天仍通过原 Run 查看。

## 3. 数据与权威事实

- `RunState.rerun.origin`：successor 的来源 Run UUID、精确 round/node/attempt、操作 ID、继承截至的 round index/trace sequence、所用 authoring revision。
- `RunState.rerun.sealed_by`：来源 Run 的首次交接事实；用于拒绝 runtime 继续、人工检查、执行计划当前修改和 ACP 追问。封存不改变原终态结果。
- 来源 Run 下按稳定操作 ID 保存重跑记录，记录完整目标初始 Run、Workflow 与 model bindings；目标目录只保存恢复定位。相同来源 UUID 和完整失败 locator 只生成一个 successor；不同历史失败 attempt 可分别分叉。
- 原 `RunState.status/outcome/execution` 仍为唯一运行生命周期。origin/seal 只表达现有 current/trace 无法表达的跨 Run 来源与写边界，不另建运行状态机。

successor 保留来源 round 编号及到锚点为止的 canonical trace。继承 NodeState 使用新本地 UUID、清空 runtime execution identity，并只物化 node.json、产物、附件。Run origin 水位明确区分继承和本次执行，继承内容不产生执行事件、不消耗新的 repair/new-round 预算。目标追加新 attempt，其后的旧 trace 与文件均不继承。

## 4. 接口与准入

写接口携带 project/task/run 和 expected round/node/attempt 完整 locator，返回稳定 operation ID、新 Run 与新 attempt locator。只接受 canonical trace 内、Completed 且 outcome=Failure/Invalid 的普通 Worker。目录存在不能证明 attempt 已提交。

先拒绝来源 `ErrorBlocked`、非 Workflow、未完成节点、人工检查待决、无效身份、不可执行定义和丢失工作区。使用任务最新 authoring 定义并记录 revision，目标仍须存在且为 Worker；继承节点的输出依据持久化 resolved config，避免用新定义解释旧产物。

同一操作重投先恢复或返回既有 successor，不重新启动 driver。错误使用现有结构化 RuntimeErrorInfo，前端本地化。旧的 current-node retry 命令语义不变。

## 5. 提交、取消与恢复

1. 锁外执行结构/绑定/执行校验、profile 和工作区预检；确定 canonical 前缀与复制规模。
2. 按既有顺序获取 authoring/来源 dispatch 写保护，复核 revision 和准入；原子预留新 Run 目录，写重跑记录和目标恢复定位，登记现有 runtime recovery candidate。
3. 来源仍在运行时通过既有 stop/fencing 路径暂停；提交 seal，阻止新调度和追问。取消来源活动会话，按实际活动状态有界等待收敛；未收敛时返回可恢复错误，不能启动第二个写工作区的执行。
4. 在封存后物化前缀、目标新 attempt、初始 plan 和 round，最后发布目标 run.json，之后启动现有后台 driver。来源状态和历史结果保留。
5. 任意写入中断均可由重跑记录重入。发布前崩溃只处理有候选、有 seal 的操作；启动恢复完成物化并按 ProcessInterrupted 暂停，不擅自执行 provider。发布后使用现有 runtime 恢复机制。run.json 是目标可见提交点。

ACP admission 与执行前复核使用来源 dispatch 读保护和同一可写性契约；封存后迟到 admission/queue dispatch 不能启动新追问。旧 provider 结果仍由 execution identity 拒绝推进。

## 6. 会话、工作区与副作用

目标从新会话开始。继承 attempt 不带 worker-ref、ACP snapshot/timeline/raw；后续首次访问继承节点时从新会话开始，同一新 Run 内之后的 Continue 边仍沿用现有机制。

目标是新 round 的初始入口或该入口连续 retry 链中的失败 attempt 时，新会话必须重新获得稳定前缀产物与上一 round 的 `$new-round` 触发上下文。作用域从已有 canonical trace 派生，与同 Run 当前节点 retry 共用判定；不能按首个精确 attempt 或仅按同名节点判断。普通 workflow edge 回返入口及其后续 retry 不重新获得首次入口的跨轮上下文，后继节点仍只接收本轮前序。

继承来源实际主工作区或 worktree，不使用当前 UI 选择或静默 fallback。不回滚文件、Git 提交和外部副作用；确认文案说明会停止来源执行、从目标重新执行后续节点，现有工作区更改保留。已删除或失效的 worktree 明确拒绝。

同一来源的 handoff 串行化且同一失败 locator 幂等；不同历史失败 locator 可以分别生成 successor。新 Run 之间沿用项目现有的工作区并发语义，本方案没有额外提供跨 Run、跨 Task 的全局工作区排他。

## 7. UI 与加载

图中最新失败 attempt 提供“从此节点重跑”；右键菜单列出可重跑的历史失败 attempt，精确提交选中 attempt。当前异常暂停仍显示“重试当前节点”。提交期间显示目标级 pending；成功导航到新 Run；迟到响应不能替换用户已切走的页面。

复用现有确认对话框与菜单组件，七种语言同步。VM 从同一后端准入规则投影能力；`ErrorBlocked` 的当前和历史入口均不显示。来源封存后 composer/runtime 继续动作不可用，历史仍可阅读。

不在普通 Run 列表或首屏读取重跑记录、聊天正文及复制资源。操作读取选定来源 Run 的 round 元数据，解析前限制最多 4096 个目录项、累计 8 MiB；只加载选定 canonical 前缀的节点和资源。设置最多 4096 个继承 trace step、4096 个资源项（文件和子目录）、256 MiB 继承资源上限。校验和复制均在 blocking pool，越界用结构化错误拒绝，不能静默截断。拒绝符号链接或越界资源。

## 8. 验收与自评

接口回归覆盖：当前已完成失败、已结束 Run、历史失败、旧下游排除、前缀输入与预算、精确身份/未提交尾部、最新定义与目标删除、ErrorBlocked、重复与并发请求、封存门禁、恢复中断和旧 execution 迟到写入。Web 覆盖历史 attempt 实际菜单、确认、pending、接口映射及新 Run 导航。执行定向 Rust/Web 测试、格式检查、前端类型检查与生产构建，并启动前端用内置浏览器验收。

过度设计评审：增加的只有来源/交接事实和可重入操作记录；均对应跨 Run 身份、幂等与多文件崩溃恢复的不变量，复用现有生命周期和锁，不迁移会话所有权。

性能影响评审：设 R 为来源 round 数量、T 为受限 round 元数据内 trace 数量、P 为继承 step 数、F 为资源项数、B 为复制字节数。round 排序为 O(R log R)，canonical trace 排序总计不超过 O(T log T)，节点校验与资源复制为 O(P + F + B)。上述输入均有显式上限；内存保存有界元数据和路径列表，文件内容流式复制。无全任务历史或 Raw 扫描、无 provider 调用持锁、无新增缓存/队列。I/O 在后台；来源交接锁覆盖该 Run 的有界停止与物化，不阻塞其他 Run；普通刷新不增加重数据加载。

## 11. 2026-11-13～14 后代执行交接修复

审查确认停止与交接契约存在三处实现缺失：重跑只等待来源 Run 目录下的 ACP，而 child Workflow Run 存储为 sibling；首次 child 的 `childRunId` 在同步执行结束后才写入父图，导致父停止无法发现正在启动的 child；同一持久化状态在 parent 与执行 worktree 下使用不同锁键，停止与继续无法共享临界区。能力边界保持 Workflow-only 普通 Worker，AI-DYNAMIC/AUTO Run 与内部节点不增加单节点重试。

复用 `DynamicNodeState.childRunId`、PreparedRun、现有 graph 状态锁与 child continue 的 execution generation 提交；准备工作及 provider 执行在锁外，锁内复核父 outer/leaf generation，先提交归属再驱动 child。attempt、dynamic graph 与 continue lease 统一按 `runtime_root` 定位。父图写入成功后紧接着进行无失败点的内存 accept；硬退出不会执行 Drop，child 与既有 recovery candidate 已持久化；后续投影失败保留 child 并暂停，无需新增跨文件事务或持久化阶段。

来源暂停与封存后，按现有图关系收集执行树并逐个暂停，最多 256 个 Run、累计 8 MiB Run/graph 元数据；取消和等待只消费该树中的 live prompt registry，保留 10 秒 deadline 和可重入 `source-busy`。循环、重复 child、缺失 Run、错误父 locator、符号链接元数据、越界和超限拒绝交接，暂停与图持久化异常复用结构化 retry 错误。successor 的 `run.json` 仍为停止完成后的可见提交点。

验收覆盖 sibling child 和嵌套 grandchild 的取消及实际停止等待、无关 Run 隔离、忙碌时不发布 successor 与原操作恢复、首次 child 在 provider 启动前可被父停止发现、已有和新建 child 在 preflight 期间被父停止后不得启动、投影写入失败保留 child、worktree 下锁和 resume channel 一致性，以及非 Workflow 模式的公开接口拒绝且不发布执行。补充 `quiesce_preserves_completed_execution_tree_history` 固定终态保护：已完成 Run/graph 的状态、outcome 与图文件字节不变，同时必须取消并等待 child 的残留 ACP 活动。

修复前失败证据：sibling 场景在“必须先取消活跃 child”断言失败；provider 已收到 child invocation 时父图 `childRunId` 仍为 `None`；worktree 对同一状态取得不同控制锁。补充边界测试还确认外部 child Run 链接被错误接受，暂停状态损坏返回 `internal.unknown`。以上复现测试修复后均已转绿。
