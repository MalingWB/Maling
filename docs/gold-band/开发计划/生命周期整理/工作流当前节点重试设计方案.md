# 工作流当前节点重试设计方案

> 状态：已实现并完成定向验收
>
> 方案日期：2026-11-09
>
> 并发与执行计划一致性修订：2026-11-10，见第 20 节。
>
> 适用范围：Conversation Workflow 模式中的外层普通 Workflow 节点，且仅限尚未进入终态的当前 Run；Direct、AUTO、AI-DYNAMIC 内部节点、已完成 Run 的重跑和历史节点重跑不在本方案范围内。
>
> 本次评审结论：保留“原 Run 内创建同 node 新 attempt”的主设计；删除 `Completed -> Running` 原地复活和 `ErrorBlocked` 绕过路径；以 `run.current*` 作为当前位置转移的跨文件提交标记，并补齐 canonical trace、幂等重投和 accepted operation identity 契约。

## 1. 背景与问题

会话页运行图的右键菜单已有“从该节点重试”文案，但实现是硬编码禁用项，没有点击回调，也没有节点状态判断。后端存在 `retry_run(task_id, run_id)`，它能从 canonical `current_round/current_node/current_attempt` 创建新 attempt，但公开命令缺少四类关键契约：

1. 没有校验当前节点是否处于可重试失败状态。
2. 没有 expected locator CAS 条件，旧图迟到点击或重复点击可能重试到已经变化的节点。
3. 没有后台 accepted 语义，桌面命令会同步等待 workflow 驱动结束。
4. 前端会话页运行图没有接入命令，旧 Run 详情入口也无法携带完整 attempt locator。

因此，本方案把“当前失败节点重试”显式建模为受限、可并发防护的独立操作，而不是把现有 `retry_run` 直接接到菜单上。当前 Run 一旦进入 `Completed`，生命周期不可回退；`Completed + Failure` 必须交给 successor run / handoff 能力，不由本命令原地复活。

## 2. 与既有能力的关系

| 能力 | 触发对象 | Run 身份 | ACP session | 适用状态 | 状态 |
| --- | --- | --- | --- | --- | --- |
| 停止 / 继续 | 当前暂停 attempt | 原 run、原 attempt | 继续原 session | ProcessInterrupted、RuntimeAbnormal | 已有 |
| 当前节点重试 | 当前失败 attempt | 原 run、同 round、同 node、新 attempt | 新 session | 未终结 Run 中 `Paused + RuntimeAbnormal` 的未完成 attempt | 本方案 |
| 完成 Attempt 重跑 | 任意失败的普通 Worker attempt | 新 successor run | 新 session；不迁移旧 session ownership | Completed + Failure/Invalid | 由《工作流失败节点重跑技术方案》实施 |

本方案与[工作流失败节点重跑技术方案](./工作流失败节点重跑技术方案.md)是不同能力。完成失败 attempt 的重跑创建 successor Run、封存来源 Run、使用新会话并保留必要输入前缀；本方案只在原 Run 尚未终结且当前失败位置创建新 attempt，使用该 Run 当前已发布的 execution plan，不迁移历史前缀，不封存旧 Run。旧《工作流节点Attempt重跑与Run封存迁移方案.md》中的 ACP ownership 迁移等扩展暂不实施。实施本方案仍删除不安全的公开 `retry_run` 入口，避免它与 successor Run handoff 竞争。

## 3. 目标语义

用户在会话页运行图右键当前失败节点并选择“重试当前节点”后：

1. 在同一个 task、run、round、node 下创建新 attempt。
2. 旧 attempt、产物、附件、ACP session 和日志完整保留。
3. 新 attempt 使用新 ACP session 和新产物目录。
4. run current pointer 指向新 attempt，并按提交时仍有效的 Run execution-plan revision 从该节点继续驱动；新 attempt 的调用配置创建后不随计划更新而回写。
5. 下游节点不回滚、不删除；本能力只用于尚未成功推进的当前失败节点。
6. 命令在权威状态提交后立即返回显式 accepted DTO，携带新 attempt locator 和由完整 locator 稳定派生的 `operationId`；长执行进入后台线程。
7. 重复点击、并发请求和旧图迟到请求最多创建一个新 attempt。

## 4. 非目标

- 不支持右键任意历史节点并从该节点重跑。
- 不修改 `workflow.snapshot.json`，不直接把 Task authoring 注入原 run；当前 Run 配置变更仍须通过既有 execution-plan 发布流程。
- 不回滚 Git 工作区或删除下游产物。
- 不复用旧 attempt 的 ACP session；重试始终创建新 session。
- 不处理 AI-DYNAMIC 内部 dynamic leaf、child workflow invocation 或 AUTO 图。
- 不引入 Temporal、Airflow、Kafka 等通用 workflow、队列或事务框架。
- 不新增 SQLite 事实源；SQLite 仍是可重建派生索引。

## 5. 数据结构与事实源

不新增持久化字段，继续使用既有结构：

- `RunState.current_round/current_node/current_attempt`：当前执行位置的唯一 canonical 事实。
- `RunState.execution`：Workflow Runtime 生命周期与恢复事实。
- `RoundState.trace`：执行路径与 attempt 历史。
- `NodeState`：单个 attempt 的状态、outcome、manual check 与 runtime execution 身份。
- Run execution plan 的 manifest 与 revision：当前 Run 已发布的可执行定义及其 `plan_revision`。
- `workflow.snapshot.json`：创建时副本与旧 Run 的 revision 1 迁移输入，不再作为重试的最新计划事实源。
- `worker-ref.json` 与 attempt 目录：ACP session 与产物归属。
- `RuntimeCandidateRegistration`：后台执行所有权与崩溃恢复候选事实。

`run.current_round/current_node/current_attempt` 是 retry 新 attempt 与新 trace step 是否已提交的 durable commit marker，不是同 locator 内部状态更新的通用事务 revision。`RoundState.trace` 只是路径投影，不能从 trace 尾部反推出当前 attempt。对 `run.current_round` 指向的当前 round，所有执行、恢复、Graph VM、历史投影和幂等判断都必须先按 current locator 截断到 canonical trace 前缀。目标 round 的 `index` 严格小于当前 round 时，必须已 `Completed` 并使用完整已校验 trace，否则是损坏状态；`index` 更大的 round 视为未提交/孤立状态并忽略；相同 `index` 却不是 current round 则是 identity 冲突。

核心身份是完整 locator：

```text
(project_id, task_id, run_id, round_id, node_id, attempt_id)
```

前端展示、请求、pending 去重和错误参数都携带完整 locator，禁止只传 run id 后依赖当前指针猜测用户意图。

## 6. 可重试条件

后端新增纯 readiness 函数作为唯一判断来源：

```rust
enum CurrentNodeRetryReadiness {
    Ready,
    RunActive,
    RunTerminal,
    RunNotRetryable,
    AttemptNotRetryable,
    ErrorBlocked,
    ManualCheckPending,
    UnsupportedNode,
}
```

同一纯生命周期函数服务命令校验和 `GraphNodeVm.retryable` 投影，前端不得复制另一套状态字符串规则。Run execution plan、Agent、profile、模型和 Git/worktree 属于命令提交前的 executable preflight，不塞进 Graph VM 的常数级 readiness；因此 `retryable=true` 表示生命周期允许发起操作，不承诺环境 preflight 一定成功。

幂等重投使用同一 canonical trace helper：当 trace 中存在相邻的 `expected attempt -> current attempt` 两个同 node step，后一个 `edge_outcome=retry`，且 current pointer 指向后一个 step 时，判定为首次 retry 已提交；以相同 `operationId + locator` 重建 accepted DTO，其中 `run` 返回重投时的最新权威摘要。本方案不新增 accepted response 持久化，因此不承诺字节级复现首次 DTO。不能只比较 attempt 数字或目录最大值。该幂等命中优先于 `RunActive`、`RunTerminal` 和其他 readiness 拒绝，因为它确认的是同一已接受操作，而不是发起第二次 retry。若相邻 step 的 `from_node_id`、node 或 round 不一致，则不得判定为同一操作。

### 6.1 必要条件

1. 任务模式为 Workflow。
2. `projectId/taskId/runId` 解析到同一权威 run。
3. run 的 `current_round/current_node/current_attempt` 完整。
4. expected round、node、attempt 与权威 current locator 完全一致；唯一例外是权威 current attempt 已经是该 expected locator 的直接 retry successor，此时作为同一请求的幂等重投返回同一 accepted operation identity 和最新 Run 摘要，不再创建 attempt。
5. 目标为外层普通节点，即 `NodeType::Worker`；`NodeType::AiDynamic` 第一阶段不支持。
6. run 必须是 `Paused`，不得是 `Running`、`Completed`，也不得处于 stopping、starting 等活动或过渡阶段。
7. 当前 attempt 不允许 `manual_check_pending`。
8. run 的 `pause_reason` 必须是 `RuntimeAbnormal`，当前 node 必须是 `Paused + outcome=None`，且没有仍在推进的 runtime execution。
9. `ErrorBlocked` 表示 workflow、DSL、control edge、缺失 continuation identity 或 runtime invariant 等当前路径不可继续的阻断，第一阶段一律不得通过当前节点重试绕过；修复定义或环境后创建 successor/new run。
10. `RunStatus::Completed` 无论 `RunOutcome` 为何都不可由本命令回退；`Completed + Failure` 使用 successor run 能力。
11. `ProcessInterrupted`、`WaitingForUserInput`、`PermissionRequested` 走继续、补答或审批路径；`Paused + RuntimeAbnormal` 但当前 node 已 `Completed + Success` 时走既有 `recover-completed-attempt`，均不显示重试。
12. Run execution plan、Agent 绑定、resolved profile、模型配置和 Git/worktree executable preflight 通过，且提交时 `plan_revision` 仍与预检版本一致。

### 6.2 拒绝场景

| 场景 | 错误码 | 用户动作 |
| --- | --- | --- |
| run 正在执行或停止中 | `workflow.retry.run-active` | 等待终态或先停止 |
| run 已进入终态 | `workflow.retry.run-terminal` | 使用 successor run / handoff |
| 当前 attempt 成功或非失败暂停 | `workflow.retry.node-not-retryable` | 使用继续或查看历史 |
| run 为 error-blocked | `workflow.retry.error-blocked` | 修复阻断原因后创建 successor/new run |
| 人工检查等待中 | `workflow.retry.manual-check-pending` | 先处理人工检查 |
| AI-DYNAMIC 内部或外层节点 | `workflow.retry.unsupported-node` | 使用既有继续能力 |
| expected locator 不匹配，且 current 不是它的直接 retry successor | `workflow.retry.stale-locator` | 前端刷新最新 run |
| execution plan、Agent、profile 或 Git 校验失败 | `workflow.retry.workflow-invalid` | 按结构化错误修复配置 |
| 预检期间发布了新的 execution-plan revision | `conversation.execution-plan.revision-conflict` | 刷新计划后重新提交；本次不创建 attempt |

错误使用既有 `CommandErrorVm { code, params }`。`workflow.retry.*` 的 params 至少包含 `taskId`、`runId`；stale locator 额外包含权威 locator，复用的 execution-plan 版本冲突携带预检版本与当前版本。后端不生成对客文案。

## 7. 命令契约

删除公开 `retry_run(taskId, runId)`，新增：

```text
retry_current_node(
  projectId: String,
  taskId: String,
  runId: String,
  expectedRoundId: String,
  expectedNodeId: String,
  expectedAttemptId: String,
) -> RetryCurrentNodeAcceptedVm
```

前端 DTO：

```ts
export interface RetryCurrentNodeRequest {
  projectId: string;
  taskId: string;
  runId: string;
  expectedRoundId: string;
  expectedNodeId: string;
  expectedAttemptId: string;
}
```

```ts
export interface RetryCurrentNodeAcceptedVm {
  run: RunSummaryVm;
  operationId: string;
  locator: {
    projectId: string;
    taskId: string;
    runId: string;
    roundId: string;
    nodeId: string;
    attemptId: string;
  };
}
```

首次返回值是 accepted 落盘后的权威 Run 摘要和新 attempt locator；`operationId` 由后端共享 helper 根据完整新 locator 稳定生成，前端只把它当作 opaque ID，不自行拼接，不新增业务持久字段。幂等重投时 `operationId + locator` 保持不变，`run` 使用当时最新权威摘要。accepted 只表示提交已可靠落盘，不表示后台执行已经开始或完成；后续进度由 run snapshot、live lifecycle event 和会话事件流提供。

Tauri 命令采用 `async fn`，通过既有 `spawn_blocking_command` 执行完整准备与提交链路，包括 heartbeat 记录、workspace / App 解析、executable preflight、锁等待、状态落盘和后台驱动交接；这些操作不能在窗口主线程或 async runtime 调度线程同步执行。命令等待 blocking job 的 accepted 结果，不提前返回成功，也不增加第二层操作队列。

## 8. 状态转换设计

### 8.1 准备阶段

1. 按 `projectId` 解析命令所属 App，校验 task/run 作用域和桌面端现有 single-instance / runtime recovery 边界；本命令只承诺同一桌面 runtime instance 内的并发安全，CLI 或其他独立进程写入另行设计。
2. 先短暂获取 expected attempt lock，重读 durable run/round：若 current 已是 expected 的直接 retry successor，立即用同一 operation identity 和最新 Run 摘要重建 accepted DTO；若既不相等也不是直接 successor，返回 stale；只有 current 仍等于 expected 才进入后续准备。
3. 释放锁后通过 execution-plan store 读取当前已发布计划，记住 `plan_revision`，从该版本构造 executable workflow 并执行结构校验；旧 Run 的迁移也在此完成。
4. 校验 Agent 绑定与 resolved profile；包含 AI-DYNAMIC 的计划沿用既有 Git/worktree 前置检查。
5. 构造 readiness 所需的权威 run、round、node 读取计划。不在旧 attempt 锁内执行网络、provider 启动或长时间 I/O。

### 8.2 提交事务

固定按 execution-plan dispatch read lock → 旧 attempt runtime state lock 获取锁，保持到 node → round → run 提交结束。最终幂等依据仍是 durable expected-locator CAS，桌面 single-instance 边界负责排除独立进程并发；provider 执行与环境预检均不在临界区：

1. 再次重读 durable `run.json`、`round.json`、`node.json`。
2. 先重复执行幂等 successor 判断，覆盖准备阶段中另一请求已经提交的竞态；命中时返回同一 operation identity 和最新 Run 摘要。否则校验 expected locator 与 retry readiness，再读取 current plan 并比较预检记录的 `plan_revision`。版本变化返回已有 `conversation.execution-plan.revision-conflict`，携带 `expectedPlanRevision / planRevision`；不得登记 candidate 或预留 attempt。幂等命中优先于版本冲突。
3. 登记 provisional runtime candidate；token 写入待提交的 `run.execution`。run 写入前任一步骤失败必须显式 abort registration；进程在中间崩溃时允许多留 candidate，启动恢复按 canonical Run 状态消费，不得据 candidate 反推 Running。
4. 将现有 `next_attempt_id` 的“读取最大编号后返回字符串”改为共享 `reserve_next_attempt_dir`：从 current attempt 的下一个编号开始原子创建候选目录，目录已存在时递增重试，允许因崩溃遗留目录产生编号空洞。不得通过一次“扫描最大编号再写入”承担并发唯一性。
5. 先以旧 current locator 截断 `round.trace` 为 canonical 前缀，再从版本已复核的 validated execution plan 创建 fresh `NodeState`：
   - 新 attempt id；
   - status = Running；
   - outcome = None；
   - started_at = 当前时间；
   - finished_at = None；
   - manual_check_pending = false；
   - 新 runtime_execution_id；
   - resolved config 来自该 execution-plan revision 加权威运行配置注入。
6. 更新 round：status = Running、outcome = None，并在 canonical 前缀后追加 trace step；新 step 的 node 为新 attempt，from_node_id 为同 node，edge_outcome 为 retry，sequence 使用既有单调规则。任何旧的、未被 current pointer 提交的尾部 step 都不再写回。
7. 更新 run：status = Running、outcome = None、pause_reason = None、current_attempt = 新 attempt，current_round/current_node 不变，execution transition 到 StartingNode 并携带新 locator 与 recovery candidate token。
8. 按既有顺序持久化 node -> round -> run；三份文件都使用原子替换。只有 run 写入成功、current pointer 指向新 locator 后，retry 才算 durable accepted。
9. commit runtime candidate；若随后后台 spawn 失败，走既有 terminalize，不返回第二个 accepted 结果。
10. 追加 `run_retry_requested` progress event，上下文使用新 attempt locator；事件只能在 durable commit 后发布。
11. 返回 `RetryCurrentNodeAcceptedVm`，后台驱动由同一命令在返回前完成 spawn 交接。

```text
旧 attempt: Paused/RuntimeAbnormal, outcome=None
    |
    | retry_current_node + expected locator CAS
    v
新 attempt: Running/None, 新 ACP session
run: Running/None, current -> 新 attempt
round: Running/None, trace += retry
```

### 8.3 后台驱动

1. 使用 `clone_for_background()` 的 App 驱动新 attempt。
2. 复用 `drive_from_node...` 主链路，不复制 workflow 调度逻辑。
3. 后台线程使用独立名称，例如 `gold-band-run-retry`。
4. 驱动 panic 和错误走既有 background terminalize 收敛，不允许永久 running。
5. 后台结果通过现有 conversation runtime callbacks / lifecycle event 发布，不创建第二事件通道。
6. 新 attempt 运行中再次重试因 `RunActive` 拒绝。

`AcceptedRun` 的 Drop 语义服务于新 run 目录清理，不能直接复用于既有 run。可实现一个仅保存 validated workflow、resolved profiles、run、round、fresh node 和 operation locator 的 accepted retry 数据结构；它是后台所有权载体，不是新的业务 aggregate。

## 9. 并发、幂等与崩溃语义

### 9.1 重复与并发请求

- 旧 attempt lock 串行化同一位置提交；桌面 single-instance 边界与 durable expected-locator CAS 覆盖本命令声明范围内的最终提交边界，进程内锁本身不被当作跨进程保证。
- 固定 Workflow 的“继续”、`recover-completed-attempt` 与 retry 均先在同一 attempt lock 内复核权威 locator、状态及各自的 revision 条件，验证成功后才登记 recovery candidate，并持锁到 canonical Running 提交。迟到的失败请求不得覆盖已接受执行的 token；仅靠清理时比较 token 无法修复此前发生的覆盖。
- 预检期间计划发布成功则本次 retry 返回 revision conflict，重新提交会重新预检新计划；retry 已进入提交临界区则计划发布等待或按既有写锁契约拒绝。后台 provider 不持计划锁，已创建 attempt 的调用配置保持冻结。
- 第一个请求提交后 current attempt 改变。
- 第二个相同请求在锁内重读权威状态；若 canonical trace 证明 current attempt 是 expected attempt 的直接 retry successor，则返回与首次相同的 `operationId + locator` 以及当前最新 Run 摘要，不创建 attempt-003。
- current locator 已发生其他推进、再次 retry 或切换 Round，且不再是 expected 的直接 retry successor 时返回 stale；此时前端刷新即可看到首次操作的历史结果，仍不得再次创建 attempt。
- 前端按完整 locator 管理 pending，双击先本地去重；后端条件是最终事实源。
- 请求超时或返回丢失后，只要 current 仍是直接 retry successor，同一请求可安全重投并取得同一 accepted operation identity 与最新 Run 摘要；若执行已继续推进则返回 stale，用户通过刷新历史收敛。前端不自动重投 stale locator。

### 9.2 崩溃窗口

| 崩溃点 | durable 结果 | 恢复语义 |
| --- | --- | --- |
| candidate/attempt 目录已预留、node 尚未写 | 旧状态仍是 canonical，可能多留 candidate 或空目录 | 启动恢复按旧 Run 状态消费 candidate；下次预留跳过目录编号，可再次重试 |
| node 已写、round/run 未写 | 新 node 是未引用历史 attempt | 下次编号跳过，不投影为 running |
| round 已写、run 未写 | round trace 可能暂时包含 retry 尾部，但 current pointer 未变 | 所有读路径截断到旧 current locator；下一次同一位置提交先规范化并清除未提交尾部，未引用 attempt 不驱动 |
| run 已写、后台未启动 | current 指向新 running attempt | 启动恢复按 ProcessInterrupted 收敛为可继续暂停 |
| 后台执行失败 | runtime terminalize | run/node 收敛为失败或可恢复暂停 |

跨文件提交沿用既有 node -> round -> run 顺序，不引入分布式事务或 journal。`canonical_trace_for_round(run, current_round, target_round)` 是 trace 消费者的统一入口：目标为当前 round 时必须截断到唯一 current step，不存在或重复时判定为损坏并拒绝写入；更早 round 必须已完成并返回完整已校验 trace，未完成则判定为损坏；更晚 round 视为未提交/孤立状态并忽略；相同 index 却不是 current round 则拒绝为 identity 冲突。不得猜测 trace 尾部，也不能把孤立 node 目录或未提交 trace step 反推为当前执行。

## 10. ViewModel 投影

`GraphNodeVm` 新增：

```ts
retryable: boolean;
```

规则：

1. 仅外层普通运行图节点可置 true。
2. 仅当前 canonical node 可置 true。
3. readiness 必须为 Ready。
4. `attemptId` 必须存在。
5. AI-DYNAMIC 内部节点、历史节点、成功节点、running 节点和 manual check pending 节点均为 false。

`RuntimeDisplayVm.resumable` 继续表达“继续原 attempt”，不得复用它推导重试。`retryable` 表达“在同 node 创建新 attempt”，两个布尔值语义并列。

运行图投影只对 canonical current node 调用同一 readiness helper；状态判断为常数级，canonical trace 校验复用已加载的 current-round trace，整张图最多增加一次 `O(t)` 处理，不新增目录扫描或逐节点历史读取。

1. 点击时置 pending，重复点击忽略。

6. 其他错误保留当前图和会话数据，在当前操作位置展示结构化错误。

## 15. 测试与验收

### 15.1 Rust 接口测试

- 失败 current node 重试：旧 attempt 保留，新 attempt 创建，canonical trace 追加 retry，run 指向新 locator。
- `Paused + RuntimeAbnormal` 且当前 node 为 `Paused + outcome=None` 时可重试；success、failure、invalid、killed 等终态 outcome 不可重试。
- ErrorBlocked、ProcessInterrupted、等待输入和权限等待不可重试；`Paused + RuntimeAbnormal` 下的 `Completed + Success` 使用 `recover-completed-attempt`，不创建新 attempt。
- Completed + Success / Failure 都拒绝原地 retry，且 run status/outcome 保持不变。
- manual check pending 拒绝且状态不变。
- running、stopping 拒绝且状态不变。
- AI-DYNAMIC 外层与内部节点拒绝。
- expected locator 任一字段不匹配且 current 不是直接 retry successor 时返回 stale，不创建 attempt。
- 并发或响应丢失后的相同请求只创建一次 attempt；current 仍是直接 retry successor 时重投返回同一 operation identity，已经继续推进时返回 stale 并由刷新收敛。
- Continue 先提交时 retry 被 RunActive 拒绝；retry 先提交时迟到 Continue 或 completed recovery 被拒绝；失败方不得改变 active registry 或 durable recovery token。
- 两个同时进入预检的 retry 只创建一个 attempt、启动一次 provider，并返回同一 operation identity。
- 预检期间发布新计划时，不创建 attempt；重新提交使用新 goal/model。provider 运行期间仍可发布后续计划，已创建调用配置保持不变。
- 预先存在孤立 attempt 目录时原子预留跳过冲突编号，仍只提交一个新 attempt；目录编号空洞不影响 canonical trace。
- `retryable=true` 但 executable preflight 失败时返回 workflow-invalid，状态不变，不把环境校验塞进 Graph VM。
- 含 AI-DYNAMIC 的 execution plan 保留 Git/worktree 前置校验。
- 后台驱动错误收敛，不永久 running。
- accepted DTO 携带稳定 operation identity 与新 locator；幂等重投保持 identity 不变并返回最新 Run 摘要；spawn 失败和重启恢复只产生一次 terminalize。
- node、round、run 写入顺序、canonical trace 截断、孤立 attempt 与孤立 trace step 读投影符合崩溃表。
- CLI 或不同 runtime instance 的并发写入不属于本命令范围，必须使用 successor run / handoff 或另行定义的写入 gate；不能以进程内 Mutex 冒充跨进程 CAS。

## 16. 性能与过度设计评审

不新增持久字段、队列、缓存、外部依赖或第二状态机。readiness enum、accepted DTO 与 canonical trace helper 都是既有生命周期和提交边界的显式化，不复制业务 aggregate；第一阶段明确排除需要新增结构化错误事实才能安全判断的 ErrorBlocked retry。

性能影响：

- 后端只新增常数个 JSON 文件读取；canonical trace 截断为 `O(t)`，`t` 是当前 round 的 trace step 数。attempt ID 使用原子目录预留，正常为 `O(1)`，仅在碰到崩溃遗留/冲突目录时按冲突数递增重试，不扫描该 node 的全部 attempt 目录。
- 预检使用一份计划快照，提交时只额外重读当前计划核对 revision；复用既有 dispatch read lock，不将 Agent 诊断、Git 检查、profile 解析或 provider 执行纳入锁范围。
- readiness 的生命周期字段判断为常数级；canonical trace helper 在当前 round 上执行一次 `O(t)` 截断与校验。
- 前端菜单谓词为常数级。
- Run 刷新复用侧栏已有单飞算法：每个在途 locator 仅保留当前 Promise 与一个最新后续读取，完成后释放；不缓存 Run 快照、不增加持久字段或依赖。同一 Run 的突发刷新合并读取，不扩大单次接口的数据范围。
- 右侧 workflow-view 仅在 `workflowGraph` 引用变化且该 tab 正在展示时触发一次 renderer refresh；不因每条 ACP 文本事件重新注册 renderer，也不扩大页面订阅范围。
- memo comparator 增加一个稳定 callback 比较。
- 不新增全量历史扫描、N+1 请求、无界队列或更大 React 订阅范围。

无需新增 benchmark；trace 风险局限于单个当前 round，attempt 预留不做全目录扫描，也不进入首屏或全量历史关键路径。并发、生命周期单调性和崩溃风险由接口测试、状态投影测试和桌面 single-instance 边界测试覆盖。

## 19. 评审问题修复（2026-11-09）

## 20. 并发 admission 与执行计划一致性修复（2026-11-10）

### 20.1 根因与复用决策

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| 迟到“继续”覆盖已接受 retry 的恢复候选 | candidate 按 Run 唯一，但 Continue 在 attempt CAS 前执行 upsert；随后拒绝并清理自己的 token，导致当前 retry 从恢复索引和 active registry 消失 | 把 candidate 登记放入既有 attempt 临界区，在 locator、可继续状态和 checkpoint 校验之后执行；completed recovery 的同类入口同步修正 |
| 预检期间发布新计划，retry 仍按旧计划创建 attempt | retry 预检读取了 execution plan，提交未参与既有 dispatch 锁，也未复核计划 revision | 预检记版本，提交按 plan read lock → attempt lock 获取锁，复核版本并持锁到 node → round → run 落盘 |
| 严格 trace 契约导致旧测试失败 | 最初 7 项 App 用例及整库补查的 1 项 IM 投影用例，有 current locator 却缺少对应 trace；替换 attempt 的 fixture 也没有同步 execution locator | 按生产不变量补齐 8 项用例的 fixture，不放宽 canonical trace 校验、不增加 fallback |

这三项属于已有 canonical identity、revision、attempt lock 和 candidate fencing 设计的实现不完整。标准互斥、乐观版本校验和现有执行计划组件已足够，不需要引入开源 workflow 引擎或新增共享 lease、队列、持久字段、依赖和状态机。

### 20.2 接口与提交契约

1. `retry_current_node` 请求和 accepted DTO 保持既有结构。重复 retry 仍优先返回同一 accepted identity，不因计划随后更新而创建第二个 attempt。
2. 固定 Workflow Continue 将权威提交抽为 `commit_fixed_run_continue`，生产入口与竞态测试共用；旧请求返回已有 `runtime.continue-superseded`，不登记 candidate。completed recovery 同样先复核 locator、execution revision 与可恢复条件。
3. retry 锁外完成计划加载、迁移与 executable preflight；锁内复核 current locator、readiness 和 `plan_revision`。计划冲突返回已有 `conversation.execution-plan.revision-conflict` 与版本参数，原 attempt 和恢复状态保持不变。
4. 不在命令内部自动循环重试版本冲突。用户刷新后重新提交时，重新读取并校验最新计划；新 attempt 的 goal/model/config 取自该次已验证版本，运行期间不随计划更新回写。
5. 复用现有 candidate registration 的提交与撤销语义；candidate 必须在状态校验成功后、canonical Running 写入前登记，失败方不能先替换成功方的恢复 token。

## 21. Run 刷新收敛与右侧工作流投影修复（2026-11-10）

### 21.1 根因与方案

评审发现 retry 成功后的读取与 live refresh、停止、保存和路由初始读取各自独立，迟到的旧 snapshot 可以把 `completed` Run 和 workflow graph 回退为 `running`。另外，右侧 workflow-view renderer 通过稳定注册回调读取最新 `runRef`，但 Run 更新没有触发 Dock 重绘，导致中心页已更新而已打开的图仍显示旧 projection。

修复复用侧栏已有 `RefreshSingleFlight` 算法，新增一个共享模块并让所有 Run 读取入口使用同一实例：每个 Run locator 最多一个读取在途，重叠刷新只保留一个最新后续读取；有后续读取时旧结果和旧失败不提交。retry、停止、保存在读取前后核对所属 Run 的完整 canonical identity 与当前页面，离开 Run 或 task UUID 被复用时丢弃迟到结果。右侧 workspace 增加显式 renderer refresh 信号，只在当前 workflow-view tab 的 `workflowGraph` 引用变化时触发，保持注册 identity 和资源生命周期不变。

这属于现有 canonical identity、live/snapshot 收敛和稳定 renderer 设计的消费实现不完整。没有新增后端 revision、持久字段、缓存、队列、依赖或第二套状态机；单飞读取和局部 renderer refresh 与实际突发刷新及打开资源范围匹配。

- 未修复实现下，`conversation-run-refresh.test.tsx` 的真实 App/DOM 用例稳定复现迟到 retry snapshot 把已完成 Run 和 graph 回退为 `running`。

## 22. 2026-11-11 重试命令线程隔离修复

### 22.1 根因与实现

原 `retry_current_node` 是同步 Tauri 命令。虽然 provider 驱动最后会启动后台线程，之前的 workspace 解析、Git / profile 预检、计划与 attempt 锁等待及状态写入仍占用命令调用线程。这属于 accepted 与后台驱动设计的命令适配不完整。

入口改为异步，命令执行函数把完整 App 准备、重试准入和提交移入已有 `spawn_blocking_command`，并等待其结果。函数接收拥有所有权的 locator 和一次性的 App 准备闭包，便于在命令边界固定线程与错误契约；不复制调度、CAS、幂等或持久化逻辑。前端 invoke 参数、accepted DTO 及其返回时机不变。

### 22.2 复现与验收目标

最小规模为一个重试请求和一个准备阶段门闩，不依赖生产历史、外部 provider 或固定 sleep。通过线程 ID 与首次 Future poll 的事件顺序记录调度边界：准备阶段未释放时，命令必须先返回 Pending，调用线程才能继续其他工作；随后释放门闩并检查原结构化错误完整返回。另一个接口测试验证实际重试准入错误仍携带原 task / run locator。

未修复执行路径中，`current_node_retry_command_yields_until_preparation_finishes` 在 `preparation_thread != caller_thread` 断言稳定失败（两者均为 `ThreadId(15)`），且首次 poll 直到准备完成才返回；准入错误用例通过。该证据来自实际执行线程和可控等待顺序，不把测试总时长作为窗口卡顿时长。

### 22.3 性能与过度设计复核

每次显式重试只提交一个既有 blocking job，沿用前端完整 locator 去重与后端 CAS。数据规模、读取字段、trace 复杂度、锁顺序与持锁范围不变，不新增扫描、缓存、队列、持久字段或依赖。可变准备耗时由 blocking pool 承担；真正 provider 执行继续由既有后台驱动接管，不长期占用本次 blocking job。

### 22.4 修复后验收

- 同一组命令边界测试转绿：准备门闩尚未释放时首次 poll 返回 Pending，准备线程不同于调用线程；准备失败及实际重试准入失败均保留原结构化错误与 locator，共 2 项通过。
- `cargo test -p gold-band-desktop --bin gold-band-desktop -j 1 retry -- --test-threads=2`：22 项通过，包含上述 2 项新增测试。
- `cargo test -p gold-band --lib -j 1 retry -- --test-threads=2`：43 项通过，覆盖 retry 幂等、并发去重、stale locator、预检期间计划更新及后台驱动失败收敛等既有契约。
- 前端 desktop API、Run 刷新、当前节点重试菜单和工作区 renderer 共 4 个测试文件、47 项通过。IAB 使用本地生产构建及模拟数据，确认异常节点菜单可发起“重试当前节点”，请求后节点显示运行中；临时页面和 preview 已关闭。该检查验证前端调用链路，不作为真实 EXE / provider 端到端证据。
- `cargo fmt --all -- --check` 与 `git diff --check` 通过。复用既有 blocking pool 与后台驱动，未增加状态、队列或依赖；本次线程边界修复以确定性的调度顺序测试验收，不需要额外 CPU benchmark。

## 23. 新 round 入口重试上下文修复（2026-11-13）

### 23.1 根因与方案

新 round 的入口上下文原设计正确，但消费端把作用域绑定到首个精确 attempt。入口创建新会话重试后，稳定前缀和上一 round 的 `$new-round` 触发原因随之丢失；successor Run 重跑复制前缀后追加 retry step，也会进入同一缺陷路径。

复用 round trace 中已有的 sequence、来源节点和 `retry` 标记识别本轮首节点的连续 retry 链。初始入口和该链中的 attempts 共用跨轮上下文作用域；后继节点、普通 workflow edge 返回入口及其后续 retry 均排除。稳定产物继续按既有前序规则读取，继承节点继续使用冻结的 resolved config，不新增入口状态、持久字段或补偿路径。

### 23.2 验收目标与自评

通过公共 `App::retry_current_node` 和 `App::rerun_failed_node` 构造两轮执行并捕获真实 `WorkerInvocation`：新入口 attempt 应保留前轮稳定 plan 产物、本轮旧入口 attempt 和新轮触发节点的附件/失败原因；后继 invocation 只接收本轮前序，不携带跨轮 trigger。trace 边界回归覆盖多次连续 retry、无序数组按 sequence 判定、普通边回返、回返后的 retry、同节点非 retry 边和不存在的 attempt。

过度设计评审：复用现有 canonical trace 与上下文构建入口，没有新增依赖、状态机、缓存、锁或队列。性能评审：作用域判定只扫描当前 round 的内存 trace，复杂度维持 O(t)，不新增文件读取或历史扫描；原有后台 invocation 装配与 Run 加载范围不变，无需新增 benchmark。
