# 并行工作流生成：从会话到副本的验收案例

目标不是让模型复述一遍需求，而是证明：会话材料真的进入生成对话、指定修改真的只改目标阶段、保存后能重开同一模板、副本不会丢配置或改坏原件，运行时真的并行且只汇合一次。用新的测试会话和临时干净 Git 仓库（有初始提交）；不要使用已有「发布闸门」或生产测试账号。手工向已配置的模型发送消息可能消耗额度。自动用例使用合成消息及可控 Provider，不等于已验证某个商业模型输出的质量。

## 手工输入与预期

1. **积累普通会话材料。** 在测试项目里开普通 Direct 会话，发送：“我要做交付前检查。接口组负责状态码、响应字段，界面组负责页面打开、主要按钮。两组可同时执行，最后产生一份结论。请给出步骤与验收条件，先不要改仓库。”等助手给出方案，再发送：“同意，任何一组失败都不能出通过报告；只在这个测试项目中工作。”这使核心信息分布在用户和助手的多个回合，便于验证不是只取最后一句“同意”。
2. **从源会话创建。** 打开上一步普通会话的聊天详情，用标题栏“生成工作流”（不选单条“从此处生成工作流”）。预期转到本项目的输入框并预填来源摘要，尚未创建生成任务、尚未自动向模型发送。补充：“基于刚才双方确定的方案生成一个叫‘交付前并行检查’的工作流。开始后进入 checks，并行上限 2。接口分支只跑 api-check；界面分支只跑 ui-check。两支全成功后汇合，再跑 report，失败走失败结束。请各自输出可判定的检查结果。”手动发送，处理真实待澄清项。若模型不能一次得到正确图，应记为首轮模型表现，不冒称编译成功。
3. **保存与重开。** 预期画布为 `开始 → checks → {api-check | ui-check} → 汇合 → report → 结束`。两支之间没有顺序边，开始/汇合不绑定 Agent。给执行步骤配置测试用 Agent／模型；为识别误丢配置，让 api-check 具有与默认值不同的模型绑定。点“保存为工作流”，在模板管理重开，核对模板身份、阶段 ID、角色、执行槽、模型、并发上限及失败边，记录原版快照。
4. **指定修改，而不是重做。** 从当前模板发起“对话式修改”，或在仍绑定原件的生成会话中继续。在 ui-check 卡片点“修改此阶段”（只预填），补充：“只给界面验收增加‘键盘焦点可见’；接口组、汇总、并行上限和其他设置一律不动。”发送后重看蓝图，保存并关闭重开。预期更新原模板而非重复创建；除 ui-check 的目标内容外，原来的 api-check、report、组成员与顺序、执行槽、非默认模型绑定均不变。
5. **另存与隔离。** 先试用同名“交付前并行检查”另存，预期报重名，原件不变；再以“交付前并行检查（无障碍版）”另存。副本应获得新的模板身份，保留原分支的执行绑定；重新打开副本，只在 ui-check 增加‘读屏顺序正确’并保存。回到原件核对：只有‘键盘焦点可见’，没有‘读屏顺序正确’。若生成预览在健康绑定时没有另存按钮，应如实记“此 UI 路径未提供”，不能通过人为删除原件触发恢复表单来冒充成功。模板编辑器的“保存为新的工作流”是不同入口，须分别验证。
6. **区分首步试运行与完整运行。** 入口是并行组，所以预览的首步试运行应先告知“两支、并发 2”，成功后到汇合就停，report **零次**；用已保存的模板启动正常工作流时，两支重叠执行、使用独立产物，双成功后 report **一次**。再令 ui-check 返回失败，验收结果为失败、不运行成功报告。实际重叠应由控制屏障/工作进程记录证明，不能仅凭画出并行连线或总耗时较短推断。

## 本轮实测结果（2026-11-27）

- **普通会话入口**：实际 React App 组件 + 模拟桌面数据。修复前从项目 B 打开摘要，首页仍选 A；迟到的结果能覆盖用户新输入。三个回归现已通过：回到来源项目的 Direct 草稿（不修改持久偏好、不代选 Agent），不自动发送，不覆盖已有正文；重复点击只请求一次。生成会话头部打开已有预览，不重新创建；试运行无递归生成入口。真实 EXE 只读观察时在“快速对话”首页，未重放用户真实会话中的手势。
- **可见操作**：普通 Direct 标题栏显示“生成工作流”；已生成会话用眼睛图标和“工作流预览”文字。旧预览仅在原件不可用时才出现另存表单，正常保存后找不到另存按钮（`target/verify/forge-healthy-copy-ui-red.log`）；现在保存成功后可从对应工作流标题行另存，不需要先删模板。`target/verify/forge-session-delivery-ui.log`：3 个文件 49 项通过，前端生产 TypeScript 检查通过；随后在隔离 Chrome 实际点击保存→另存→取消→再次另存：取消零次 copy RPC；提交一次携带目标工作流 ID，请求成功后表单关闭并显示新副本名称。截图 `target/verify/shots/forge-delivery-healthy-copy-20261127.png`（实际组件、模拟响应）。这些不是新 EXE 的 GUI 验收。
- **真实后端与调度**：`tests/support/forge_delivery_case.rs` 同一个真实 App 用例，调用公开创建、对话轮次合并、编译、原位修改、另存、通过模板 ID 重开、真实 trial/full 运行；对话材料及确定性检查结果为本地合成，不调用外部模型。红测发现健康模板另存会将接口阶段非默认 `gpt-5.4` 模型绑定重置为 `None`。修复后完整定义、三个执行槽/模型绑定和 `max_attempts=4` 保留，副本有独立模板和定义 ID。相同用例 1/1 通过（115.87 s）。成功首组试运行：[api-check, ui-check]，峰值 2，report 0 次；正常全流程：[api-check, ui-check, report]，峰值 2，report 1 次；仅 ui-check 返回失败：[api-check, ui-check]，峰值 2，report 0 次且最终失败。兄弟启动顺序不是契约。
- **重测**：`cargo test --locked --offline -p gold-band --test worker_bootstrap -j 1 forge_delivery_case::session_create_edit_save_as_reopen_and_run_parallel_trial -- --exact --nocapture --test-threads=1`。输出：`target/verify/forge-delivery-case-green.log`、`forge-delivery-case-binding-red.log`。相邻公共回归 `target/verify/forge-delivery-adjacent.log`：23 通过，1 条无关插件材料用例过滤。历史草稿不可按同名认领模板、原件失效时的显式另存保护保持不变。

## 截图复查：几何布局与阶段标题

此前截图证明按钮可操作、SVG 连线存在，但没有证明节点排列合理。以相同「开始 → checks → api-check/ui-check → 汇合 → report → 结束」为输入，修复前纵向布局实际将开始与分叉置于 y=51，而 worker 及下游报告都在 y=40；成功/失败标签也重叠。根因是前端把开始、分叉、汇合均作为紧凑端点绘制，又在构造 ELK 布局输入时把它们当成无出边的结束节点；画面补出的连线并没有参与分层。阶段卡片另有独立问题：三个 worker 共享 `implementation-result`，原投影拿产物键当标题，导致三步看起来完全相同。

修复复用共享布局器和既有方向，不修改 ForgeSpec 或执行 DSL。校验双方向主路径严格前进、兄弟分支同层、真实边有布局路由、失败/重试标签不挤压节点；蓝图和卡片使用同一阶段名，产物键留在技术细节。`target/verify/forge-preview-geometry-red.log` 记录几何失败，`target/verify/forge-stage-titles-picker-red.log` 记录节点名与按钮误导的独立失败。

修复后用同一存档夹具实渲：纵向依次为开始、分叉、两支同层、汇合、报告、结束，横向也保持该顺序。测量 9 条边的端点及节点/标签包围盒，正常、窄屏和横向样例均未见穿卡、裁切或标签相撞。紧凑预览按最长成功路径估算高度，不把兄弟分支重复计高，标题区也不再盖住窄屏中的开始节点。[改前](../../../../target/verify/shots/forge-delivery-healthy-copy-20261127.png) · [改后](../../../../target/verify/shots/forge-preview-layout-normal-20261127.png) · [窄屏](../../../../target/verify/shots/forge-preview-layout-narrow-20261127.png) · [横向](../../../../target/verify/shots/forge-preview-layout-horizontal-20261127.png)。布局与相邻用例 88/88，另跑预览/导入/七语言 56/56（范围部分重叠）。生产前端类型检查通过；Vite 在转译时达到为本机设置的 1,280 MiB Node 堆上限（exit 134），本次不算生产包通过，未替换已打开的 EXE。

## 验证口径

分别记录四层证据：① 当前 EXE 实际可见的页面（未经实际点击不能作为点击证据）；② 实际前端组件点击、预填与 IPC 参数（标明是否模拟响应）；③ 临时存储中的实际 App 创建、合并、编译、另存和重读；④ 真实调度器 + 可控 Provider 执行结果。App 能调用另存 API 不等于用户能在生成预览里点到。报告清楚区分普通会话头部“生成工作流”、已生成会话头部“打开工作流预览”和消息级“从此处生成工作流”。
