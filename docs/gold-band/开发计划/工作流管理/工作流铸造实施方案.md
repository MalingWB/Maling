## 1. 背景与定位

大量用户在 Claude Code 命令行上沉淀了 skill 工作流，存在切换成本。直接"导入兼容"Claude Code 格式不是差异化——我们的 skill 模块（`src/skill/`）已能扫描解析 `.claude/skills` 并完成 symlink 同步，单纯搬入没有竞争力。

真正的差异点在于两者的结构差距：

- Claude Code skill 是 prompt 片段：无结构化产物、无 success condition、无失败回环、无状态恢复；
- Gold Band 工作流（`WorkflowDsl`）具备 output 契约（schema 化 artifact）、success_condition、round/attempt 状态机、Run 级快照与恢复语义。

因此本方案的定位是：

> **任何一段自然语言或一组 Claude Code skill，通过与 Gold Band 的引导式对话（拷打/脑暴），被编译成带结构化产物、可验证、可恢复、可对话演化的工作流。**
>
> Claude Code 让用户*写*工作流，Gold Band 让工作流从对话中*长出来*，且长出来的产物比手写的更强（有契约、有状态、有验收）。

两大能力支柱：

1. **生成（Interview-to-Workflow）**：内置 `workflow-forge` 角色，引导式对话产出中间表示 Forge Spec，经确定性编译为 `WorkflowDsl`；
2. **修改（Conversational Editing）**：现有工作流反投影为 Spec 进入 Forge 会话，用户以自然语言修改后重新编译，走现有 authoring revision 保存。

非目标（明确排除）：

- 不做 Claude Code skill 格式的"一键原样导入为工作流"（skill 只作为生成对话的上下文素材）；
- 不暴露 DSL 的 `workflow_invocation` 嵌套编排给 Forge：Forge 产出平铺的线性/回环工作流，Spec 中无"引用另一条工作流"的表达项，编译器不产出嵌套结构。嵌套引入跨工作流生命周期与状态归属问题（子流程失败归属、产物归属），待真实需求出现再评估；
- 不新增存储结构：模板存储维持现有单文件 `workflows.json`；
- 不让 LLM 直接产出 `WorkflowDsl` JSON。

## 2. 核心设计决策（评审记录）

以下决策均经过与用户的设计评审确认：

| # | 决策 | 依据 |
|---|---|---|
| D1 | LLM 只产出 Forge Spec（结构化 JSON），Spec→DSL 由纯 Rust 确定性编译 + `ValidatedWorkflow` 校验 | Spec 是语义层、字段少、Schema 约束，出错面受限；edges/`$end`/session 等易错结构根本不经过模型。用户确认的是 Spec 语义层 + 编译后图预览，DSL 语法合法性由编译器保证 |
| D2 | 入口 A 提取范围为**整个会话**，首轮做"意图锚定"由用户确认；右键"从此处铸造"截断上下文为第三阶段增强项 | 黏性资产是多轮脑暴的完整上下文；锚定确认防跑偏；超长会话沿用现有 context-management 摘要压缩 |
| D3 | 流程图预览由 Spec 结构事件驱动增量更新，与 token 流完全解耦；节点上限 10 | 图更新频率与 token 流速无关；典型 2~6 节点的小图无渲染压力；详见 §6.4 |
| D4 | 节点上限三层防线：schema 硬校验（`forge/too-many-stages`）+ 对话期主动收敛 + Spec 级拆分重组（产出平行的独立工作流组，不做嵌套调用） | 拆分决策发生在 Spec 层对话内，编译与保存无状态 |
| D5 | 命名是 Spec 必收敛字段：模型在意图锚定轮给出 1~2 个候选名，用户确认；`id` 落库走现有模板 slug+随机后缀规则 | 用户全程无需从零输入；不新造重名机制 |

## 3. 数据结构

### 3.1 Forge Spec（中间表示，LLM 输出的唯一契约）

Forge Spec（下称 **Spec**，即"铸造草稿"）：对话收敛结论的结构化载体。三重角色——对话的记忆（中断恢复）、流程图的数据源（图是 Spec 的投影）、编译的输入（翻译为 WorkflowDsl）。用户无需感知 Spec 存在。

```jsonc
{
  "specVersion": "0.1",
  "name": "后端接口开发-测试-验收",      // 必收敛字段，forge/missing-name 兜底
  "intent": "一句话流程意图",
  "sourceSkills": ["code-review", "write-tests"],  // 可选，来源 skill 引用
  "workflows": [                          // 拆分时多元素，默认单元素
    {
      "name": "接口开发与测试",
      "stages": [
        {
          "role": "dev | test | review | plan | accept | custom",
          "goal": "该阶段目标",
          "artifact": "test-result",
          "outputKind": "json | markdown | none",
          "schemaHint": { /* 产物字段草案 */ },
          "successCondition": "$.passed == true",
          "onFailure": "retry | manual-check | new-round | end",
          "manualCheck": false
        }
      ]
    }
  ],
  "openQuestions": [ /* 未澄清项，驱动多轮对话 */ ]
}
```

约束：

- `stages` 数量 ≤ 10（schema 硬校验，错误码 `forge/too-many-stages`）；
- `name`、每个 stage 的 `goal` 与 `successCondition` 为必收敛字段，编译期校验兜底；
- **goal 四要素契约**：每个 stage 的 `goal` 必须覆盖——输入、产出、边界（不做什么）、验收（怎么判断完成）。缺要素视为未收敛项，进 `openQuestions` 继续拷打，不允许浅显 goal 流入编译；
- **增量生长约束**：Spec 逐轮生长，每轮对话只产出当前 stage 的增量，不做一次性全量输出，规避模型上下文/输出预算导致的截断；单 stage 输出超预算按 `forge/invalid-spec` 走 repair；围栏已闭合但只漏结尾 `}` / `]` 的增量按括号配平补全（`SpecDelta::parse`，真机上模型出现过）；
- **stage 稳定身份**：`id` 由系统在每轮合并后分配（`interview::assign_stage_ids`，`角色-序号`——`plan-1` / `dev-2` / `test-3` / `review-4` / `accept-5` / `custom-6`，序号按角色分别计、Spec 内唯一；模型省略或给出不可作节点名的值时补齐），同时是编译后的节点 id 与编辑器画布上的节点名，所以按角色命名而不是纯序号。增量**只按 `id` 对齐**：命中即整体覆盖（`profileId` 未携带时沿用基线值），不带 `id` 或 `id` 不在基线中的一律是新 stage；
- **基线随每条消息注入**：`forge_baseline_section`（`node_executor` 装配 invocation 时）把当前存档作为隐藏区段注入首条与后续每条消息；角色（system prompt，会话内不变）只承载协议规则与 Schema（`forge/spec-protocol.md`），不再写死“基线为空”；
- Spec 是唯一对话事实源：前端流程图、确认 UI 均为 Spec 的投影，不维护第二份状态。

### 3.1.1 节点内容质量与分工

节点运行时 prompt 的主体来自内置 profile（dev/test/review 等已有成熟长正文，经 `prompt-bundle` 组装），`goal` 只承担任务指令部分——模型不需要在 Spec 里输出长篇 prompt，"内容浅显"风险由 profile 正文兜底，Forge 只对四要素负责（见上）。

### 3.2 编译规则（确定性，`src/forge/compiler.rs`）

- stage → `worker` 节点：**节点 id = stage id**（同一 stage 重编译后 id 不变，才能与既有模板的节点对齐）；作者态 provider/model 置空，`executionSlotId` 在保存链路分配并补默认 agent 绑定；
- `role` → 内置 profile 选型（dev/test/review/plan/accept）；`custom` 时以 `goal` 生成 User scope 新 profile；
- `onFailure` → 边映射：`retry`→同节点回环、`new-round`→`$new-round`、`manual-check`→`manualCheck=true`、`end`→边到 `$end`；
- `control`：`max_attempts`/`max_rounds` 默认值（3/2），暴露为可调项；
- 末 stage 产生 `on: success → $end` 边；
- 产物走 `WorkflowTemplate`（`isBuiltIn=false`），`id` 按现有模板规则生成；
- **校验一次报全**：`compile_reporting_all` 收集 Spec 层（`ForgeSpec::validate_all`）与 DSL 层的全部问题（同一条去重），`compile` 是只取首个错误的快捷方式——修正轮按清单一次修复，3 轮预算不被逐个报错耗尽。

### 3.3 反投影与无损回写（修改路径，`src/forge/project.rs`、`App::forge_compile`）

- `WorkflowDsl → Forge Spec`：stages、artifact、successCondition、manualCheck 还原为对话语义层，stage id = 原节点 id；
- **无损回写**（`write_back`）：节点按 id（= stage id）对齐——命中的节点只覆盖 Spec 表达的字段（profile、goal、产物契约、成功条件、人工复核），`executionSlotId`（模型绑定的挂载点）与节点级运行配置保留原值；未命中即新增节点（取编译器产物，保存链路分配 slot 并补默认绑定）；原链上未命中的节点随 stage 删除。节点顺序、边与 entry 以重编译结果为准，`control` 等模板级可调项保留原值；
- **原位更新的适用条件**：以草稿工作流的不可变 ID 记录模板 ID、定义实例 ID 及作者态指纹，和草稿 revision、角色回填一起原子存入 `<task_dir>/forge/spec.json`。指纹取自反投影使用的同一模板快照，随后只从实际保存的模板推进；普通草稿保存不重新取基线。批次写入前校验全部目标，提交时保留库文件 CAS。原件删除、重装、不可表达、作者态已变化或旧绑定没有指纹时均拒绝覆盖，可对所选草稿显式另存或从当前模板重新发起会话。指纹覆盖模板名、节点作者态、分组和链路，不含保留节点的槽位、模型绑定或模板级执行上限；未绑定的工作流首次保存时新建。
- **逐项提交**：整份保存、编译检查传入 revision；模型增量与卡片在同一项目/任务锁内重读后合并。编译每成功一条即写其 checkpoint 并保留其他条目的目标；后项失败后重读最新草稿重试。UI 接受成功响应中的权威草稿，只向前推进 revision。
- 模板名跟随 Spec，与定义变更落在同一次落盘（`update_workflow_template_with_name`）；对应关系每落库一条模板就推进一次，后续工作流保存失败时已落库的模板在重试时被原位更新而不是重复新建；
- 模板保存沿用现有 `updated_at`，**不做 revision 历史与回退**（不在本方案范围内；总验收里对应的“revision 可回退”一条据此不适用）。

## 5. 交互流程

> 2026-11-18 评审修订（用户确认）：铸造触发方式从"会话创建后自动锚定"改为**"预填 composer + 手动发送"**——用户选好源会话/skill 后新开铸造草稿，输入框预填结构化摘要（可编辑、可补充），手动点击发送才触发铸造。锚定确认前移到发送前（用户在输入框亲眼看到并改过），且复用现有"发送即建任务、失败自动回收"机制，不产生孤儿壳会话。

1. **入口**：聊天窗"铸造为工作流"（会话级锤子入口，仅 Direct 非 Forge 会话可见）/ SKILL 区勾选 N 个 skill 或 Plugin 素材 → "从所选素材生成工作流"；
2. **预填草稿**：入口点击读取源会话摘要（`forge_source_digest`：标题+需求，预算内截断；"从此处铸造"带截断点），预填 composer 正文并绑定铸造 chip（锤子图标，可解除降级为普通会话）；完整源会话材料（需求全文+时间序用户消息，G5 预算）由后端在发送时注入首条 prompt 隐藏区段；素材入口由前端用结构化摘要（`forge_items_digest`）按界面语言拼装预填正文，素材全文同样在发送时注入；
3. **手动发送**：用户补充要求后点发送 → `create_conversation_run`（携带 `forgeSourceTaskId`+`forgeSourceAfter` / `forgeSourceItems` / `forgeSourceTemplateId`）→ 后端固定 workflow-forge 角色、注入隐藏材料、标记 `origin=forge`，任务与 run 原子创建。带着铸造标记却切换了工作区或非 Direct 模式时就地提示、不发送；
4. **意图锚定**：Forge 角色首轮总结理解到的流程意图 + 候选工作流名，用户确认或纠偏；
5. **拷打收敛**（3~6 轮）：产物契约、成功条件、失败策略、验收方式、阶段边界；stages 逼近上限时模型主动提出合并或拆分（D4）；每轮回复携带围栏 JSON Spec 增量，当前基线 Spec 随每条消息注入；runtime 在轮完成时提取合并落存档（`forge_settle_turn` → `forge_extract_turn_delta`，合并后为 stage 分配稳定 id），随后发出 `forge-turn-settled`；
6. **实时预览**：右侧工作区"铸造预览"Tab（进入 Forge 会话自动打开一次，头部锤子可重开）。自上而下：意图与动作 → 进行态/校验问题 → 编译结果 → 流程图 → 升级对照 → 阶段卡片（意图、stages 四要素 goal、产物形态/成功条件/失败策略、待澄清项）。流程图是纵向的紧凑链条（`GraphView` 紧凑密度：产物名 + 「角色 · 失败策略」两行卡片、「结束 / 新一轮」端点、失败边），随 stage 增量生长（D3）；只在收到轮次收口事件时重读存档（存档必已更新，增量无法应用时事件带原因）；
7. **编译**：预览 Tab"编译为模板"（openQuestions 清空才可用）→ `forge_compile` → Spec→DSL 确定性编译、custom 角色注册 User profile、落模板库（会话已有对应模板时原位更新，见 §3.3）；未通过时进入自动修正：后端返回全部结构化错误与修正提示词，预览 Tab 经对话栏把提示词发出（对话里显示一行"编译未通过，正在修正 N/3"，修复要求在可折叠的隐藏区段里可审计），这一轮收口后重新编译，最多 3 轮；仍不通过则带着未解决的问题回到用户对话，不静默产出坏模板；
8. **试运行**：编译成功后预览 Tab"试运行首节点"——以模板创建真实任务（`origin=forge-trial`，数据级截断保留 entry 节点 + `max_rounds=1`），样例需求 = Spec `intent`，经通用 prepare+launch 启动并导航；跑通**首个节点**即停，产物在右侧工作区正常可见，用户核对后决定保留或回对话继续修。复用 task→run 全链路，不造 dry-run 专用路径；
9. **修改**：模板列表"对话式修改" → 反投影 Spec 作为会话初始存档 → Forge 会话（基线随每条消息注入）→ 修改 → 重新编译原位更新模板。

### 5.1 生成渠道

| 渠道 | 范围 | 阶段 |
|---|---|---|
| 会话记录 | 完整会话（主路径，意图锚定确认）；某条消息"从此处开始"截断生成 | 完整会话为第一阶段，截断为第三阶段 |
| skill 组合 | 勾选一个或多个 skill（**支持跨 agent 混合**，如 Claude Code + CodeBuddy 的 skill 组合）生成。多源扫描、优先级、正文注入复用现有 `src/skill/` 能力（Project > Global > BuiltIn），skill 正文作为 Forge 会话 hidden context 注入 | 第二阶段 |

### 5.2 会话挂靠与呈现

**挂靠模型**：Forge 铸造会话 = 一个普通 Task（`origin: forge` 标记，不改 Task 数据结构），挂在用户当前/选定的项目下，复用 `ProjectManifest`/`project_id` 身份域。不新增"Forge 工作空间"层级。

**skill 入口的项目归属规则**：

- 全部勾选为项目级 skill → 直接挂靠该项目；
- 含全局 skill（全局 skill 管理页发起或混合勾选）→ 弹出项目选择对话框：框内顶部 info 文案（"铸造会话与试运行将挂靠所选项目；生成的工作流模板全项目通用"——注意：模板库是用户级全局（`~/.gold-band/user-context/workflows.json`），挂靠只影响会话与试运行的 task/run 归属，文案不得暗示模板为项目资产），列出已有项目，默认选中最近活跃项目，用户一次点击确认；首次选择后记住偏好，后续默认沿用不再重复询问；
- skill 管理页勾选栏顶部常驻提示文案（"将从所选 skill 生成工作流，需为铸造会话选择挂靠项目"），使用户在勾选阶段即有预期。文案 key 走 `web/src/locales/` 七语言同步，遵守 `ui-locale.md`；
- 无项目会话是悬空态，禁止——工作流的执行域是项目（task/run 均在项目下）。

**会话记录与左侧栏**：Forge 会话聊天记录走现有 ACP session + timeline + SQLite 索引，与普通会话同一套存储/搜索/恢复；左侧栏即现有项目会话列表，Forge 会话以徽标区分（锤子图标 + "铸造中/已产出 N 条工作流"状态）；点徽标可看本场铸造产出的模板组（关联 `sourceSkills` 与模板 ID）。未完成铸造会话不进默认列表过滤范围，通过**铸造历史**统一管理（第一阶段交付，见 §6）。

**右侧工作区预览**：复用现有"会话右侧工作区 Tab"机制（同 AUTO 配置 icon 惯例）：

- 发起铸造 → 会话创建 → 右侧工作区自动打开"铸造预览"Tab；
- Tab 内容两阶段：对话期显示 Spec 流程图（增量生长，点击节点看 goal/契约）；编译成功后**同 Tab 原位切换**为工作流编辑器预览（最终确认处），不新开 Tab 不跳页面；
- 关闭 Tab 后会话头部保留流程图 icon 可随时重开；Tab 只是 Spec 投影的消费者，关闭不影响对话，重开从当前 Spec 全量重建（≤10 节点，成本可忽略）；
- **恢复语义**：聊天历史走现有会话恢复；Spec 从 Task 落盘状态恢复（task 级 authoring 辅助事实，即铸造历史的存储位），Tab 重开即还原中断前图状态。

### 5.3 边界与异常处理

| # | 场景 | 处理 |
|---|---|---|
| G1 | 模型绑定缺失（用户未配置任何 provider） | 保存成功后检查绑定完整性，缺失时引导跳转现有模型绑定设置；不阻塞保存，仅提醒 |

> 1. **「自动重试」不会重试**：`retry` 编译成“不加失败边”，而运行时规定没有失败边等价于 `failure → $end`，阶段不通过时整个运行直接失败；`max_attempts` 只对“失败边跳到真实节点”的跳转计数。§3.2 约定的是 `retry → 同节点回环`，实现与单测（`on_failure_new_round_edge` 断言 Retry 不产生 failure 边）都偏离了方案。
> 2. **对话式修改会丢失败跳转边**：反投影把“失败边指向真实节点”一律记成 `retry`（目标节点与 `session=continue` 丢失），把 `$new-round` 边的重开起点丢掉；重新编译时边整体按草稿覆盖。真机只读核对：默认完整工作流的 `review / test -failure-> dev` 反投影后均为 `retry`。
> 3. **内置默认工作流无法对话式修改**：五类之外的内置角色（访谈、清理、拷问、开发测试）被反投影成 `custom` 并带内置 profile id，落库时对内置角色调用更新而报 `profile.readonly-built-in`。真机复现：以默认轻量工作流的反投影草稿调用 `forge_compile`，返回该错误码。

## 7. 亮点呈现（可感知差异化）

架构优越（契约/状态/恢复）是理性亮点，用户第一次看不到。可感知的呈现细节：

1. **铸造对照报告（第二阶段）**：编译完成后预览页顶部"升级对照"——左栏原 skill/会话描述（prompt 片段），右栏现在获得的能力清单（✓ 结构化产物 schema、✓ 成功条件、✓ 失败自动回环、✓ 断点恢复）。把"比 Claude Code 优越"翻译成用户一眼看懂的语言。**样式要求**：左右分栏对照，每行能力配一句白话说明（非术语堆砌），真机验收标准为非技术用户能看懂并认可；
2. **对话与图同屏生长（第三阶段）**：节点逐个长出 + 点击看契约，官网录屏/传播的主画面；
3. **铸造→分享闭环（第二阶段末）**：复用现有 `workflow_share`，铸造产物一键分享，他人导入即用——"把脑暴过程变成别人能直接跑的资产"；
4. **来源徽标**：工作流列表用**颜色 tag** 区分来源（铸造 = 主题色 tag / 导入 = 中性色 tag / 手动 = 灰阶 tag，用组件库 tag 变体实现，不用 emoji），铸造产物有身份感。

## 8. 性能与存储评审记录

- **模板存储（D6）**：单文件 `~/.gold-band/user-context/workflows.json`，现有 `write_json` 原子写 + revision 机制不变。规模分析：模板生成是人节奏操作，极端 200 条 × ~10KB ≈ 2MB，启动全量读 + 列表页本就需全量 id/name，无浪费；写频率极低，原子重写毫秒级。**拆分演化触发条件**：出现模板市场/批量导入等机器节奏写入，或单文件 >2MB 时，演进为 `workflows/` 目录 + 每模板一文件 + 轻量索引。当前预做属过度设计。
- **流程图渲染（D3）**：节点 ≤10，每次 Spec 结构变更 ≤1 次小图 diff 更新，与 token 流解耦；入场动画为一次性 CSS 成本。无热路径。
- **Forge 编译**：一次性纯函数调用，无缓存需求。
- **会话上下文注入**：超长会话沿用现有 context-management 摘要压缩，不新造机制。

### 8.2 功能自测（真机）

- 端到端剧本：自然语言会话 → 锚定 → 拷打 → 预览 → 编译 → 试运行首节点 → 保存；
- skill 剧本：混合勾选 Claude Code + 其他 agent 的 skill 生成（第二阶段）；
- 修改剧本：反投影 → 自然语言修改 → 无损回写断言（模型绑定等配置不丢）；
- spec-repair 剧本：构造会失败的 Spec（超限 stages）验证 repair 循环与 3 次上限后回退用户对话的行为。

### 8.3 性能与潜在缺陷专项检查

按 §7 评审维度逐项验证：

- **渲染**：Forge 对话 + 流程图同屏时，用 React Profiler / 性能时间线验证——token 流式期间图组件零重渲染（图更新次数 == Spec 结构事件次数）；节点 10 上限下的入场动画无掉帧；
- **加载**：铸造入口打开不阻塞聊天会话（Spec/图数据懒加载）；`workflows.json` 单文件读写耗时不随模板数线性劣化（构造 200 条模板压测启动读取）；
- **上下文**：超长会话注入走摘要压缩路径，验证 Forge 会话首 token 延迟不超基线；skill 多选注入时的 hidden context 预算控制（参照现有 50KB catalog 预算）；
- **无泄漏检查**：Spec 增量更新事件不携带整图重绘 payload；修改保存不产生额外的全量模板重写（复用单文件原子写，验证写放大不翻倍）。

### 8.4 回归与验收固化

- 8.1 的全部测试进 CI，作为后续改动回归基线；
- 试运行链路复用真实 runtime，无 dry-run 专用路径——试运行通过即等价于真实运行第一环验证，不在测试面外留盲区。
