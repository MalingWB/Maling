# 角色、Skill、插件混合生成并行工作流

## 用户路径

在「上下文管理」的角色列表勾选一个或多个内置/用户角色；也可切到「SKILL 管理」，继续勾选独立 Skill 以及 Plugin 卡片里的具体素材。跨标签使用同一份选择。只选角色也可生成，MCP 服务、插件整包不在勾选范围。选中的是**编写流程时的资料**，不是把这些角色改成会话作者、自动指定成阶段执行者或授予工具权限。项目素材只能带入其原项目；不将全局选择当作属于最近打开的任一项目。

Plugin 来源区对 WorkBuddy 的自动和手动发现分开：桌面用户登记只检查支持的确切 `installed_plugins.json` 布局；应用随附 Skill 只从已定位的 WorkBuddy 安装根读取固定后缀。未匹配的安装版本或外部目录仍可手动选取。不同来源标签不得误读为已在 ACP 会话加载。详见[兼容性证据](../../产品设计文档/Agent插件兼容性核查.md)。

## 为什么需要新的验收用例

[从普通会话生成的并行案例](并行工作流生成-从会话到副本验收.md)验证的是源会话。它不能证明角色/Skill/插件三类选择真的进入同一条生成请求。本次额外从素材入口开始，用独立临时项目、测试角色和固定的本地 Provider，验证材料与最终行为之间的联系，不调用真实账户或商业模型。

| 输入资料（每条判据只在对应正文出现） | 应体现在哪个步骤 |
|---|---|
| 用户角色：接口返回 HTTP 412 时须有前置条件回执 | `api-check` 的验收条件 |
| 项目 Skill：键盘导航必须恢复之前的焦点 | `ui-check` 的验收条件 |
| WorkBuddy 插件中的报告素材：报告要交叉引用两份回执 | `report` 的验收条件 |

同目录另放同名但不同 ID 的未选素材作对照。先看摘要再更新测试角色和 Skill 的正文，创建时应取实际选中资料的最新正文；不得带入未选内容，不可把调用方传入的角色冒充生成师。测试用作者仅能从收到的实际提示提取三条验收要求，缺一不可产生该案例的有效草稿。

## 放行条件

- UI 真正从角色、Skill、Plugin 对应卡片勾选/取消，三个标签的数量一致；挂靠、切项目、请求失败与重试不误删选择或串项目。
- 存储的三个阶段具有三条不同资料提供的具体判据。定向改一个阶段、保存、另存、重开后原件及副本仍隔离，执行槽/模型绑定维持断言。
- 在真实调度器中的两条分支分配不同 Git 工作目录、活跃区间重叠，实测峰值 2。首组试运行应不启动报告；完整成功的报告恰好执行一次且在两个分支完成之后；单支失败时报告零次。
- 分开报告：本机 WorkBuddy 安装路径/版本证据、合成桌面登记解析、角色库公共解析、真实前端渲染/模拟 IPC 与可控 Provider 下的真实调度结果。源码改动不自动更新已经打开的旧 EXE。
