# ZCode CLI 真实验收记录（2026-11-12）

## 结论

ZCode 在 Windows x64 上使用官方桌面端内置 CLI 与社区桥接器完成了真实 GLM 后端验收：initialize、session/new、真实工具、stop、session/list、session/load + history、进程清理与三层 Skill 调用全部通过。fork/continue、close/delete 语义、其他平台矩阵与 Gold Band 产品化启动配置仍未完成，因此 ZCode 继续留在第二阶段，不进入正式 Catalog。

## 安装与环境适配

1. 安装包从 `Downloads` 直接启动被本机安全软件拒绝；复制到临时目录后 `/S` 静默安装成功。
2. CLI 独立运行时找不到内置 Provider 配置。已将签名包内 `resources\config\provider\zcode-builtin.json` 复制到 `resources\glm\provider\zcode-builtin.json`；桥接器自身会检查 `resources\config\provider`，不依赖该副本。
3. 桥接器在 Windows 上无法通过自身探测找到 sqlite-capable Node，导致真实后端无法启动（日志：`no sqlite-capable node found`）。使用 `ZCODE_NODE` 显式指向 fnm 默认 Node、`ZCODE_BIN` 指向内置 `zcode.cjs` 后解决。
4. 模型选择来自 `session/new` 的 `configOptions`，默认值为 `builtin:bigmodel-coding-plan\GLM-5.3`；直接固定 `ZCODE_MODEL=GLM-5.3` 会被后端拒绝（`Provider Registry 中不存在 Model`），不能作为产品配置方式。

## ACP 生命周期：通过

运行方式：`ZCODE_NODE=<fnm node> ZCODE_BIN=<zcode.cjs> node scripts/acp-acceptance.mjs zcode-acp-server`

| 场景 | 结果 |
| --- | --- |
| initialize | 通过；`loadSession=true`，声明 `list/resume/fork`，未声明 `close/delete` |
| session/new | 通过；返回 `sessionId`、`modes`、`configOptions` |
| 真实工具回合 | 通过；Bash `ls` 完成，`end_turn`，输出包含 `TOOL_OK:D5H2` |
| session/list | 通过；返回含历史会话的非空列表，cwd 正确 |
| stop | 通过；活动 sleep 工具被取消，`stopReason=cancelled` |
| 断线恢复 | 通过；重启 transport 后 `session/load` 返回 `replayMeta`，恢复回合仍记得 `D5H2` |
| 进程清理 | 通过；关闭 stdin 后进程自然退出，无强制回收 |

## Skill：通过

在三个作用域各创建一个一次性探针，并在同一真实回合中要求模型按精确名称依次调用：

- 项目：`<cwd>/.agents/skills/accept-zcode-project`。
- 用户主目录：`~/.zcode/skills/accept-zcode`。
- 用户共享目录：`~/.agents/skills/accept-agents`。

三个 `skill` 工具调用均被观测到，输入分别为对应 skill 名称，最终返回 `SKILL_BOTH_OK`，`stopReason=end_turn`。验收后所有探针文件与新建目录已删除，`~/.zcode/skills`、`~/.agents` 恢复为不存在。

## 剩余门槛

1. fork / continue 的真实会话验收。
2. close/delete 未由桥接器声明，需确认桥接器生命周期策略与 Gold Band 有界清理契约的映射。
3. macOS / Linux / Windows aarch64 矩阵未测试，不得默认为支持。
4. 产品化启动配置：`ZCODE_BIN` 与 `ZCODE_NODE` 目前依赖手工环境；需在方案中明确发现顺序与诊断错误，不能要求用户手改系统环境。
5. 桥接器为社区项目，需按方案保留 `community-adapter` 来源标识与固定版本验收边界。
