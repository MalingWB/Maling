本方案不创建新的工作流生命周期。新增类型用于表达既有生命周期的动作投影和提交条件；工作流是否推进仍由原 Runtime 决定。

本次自评审补充仅采纳前三项：临时忙碌导致漏通知、企微慢回调缺少可靠结果反馈、UUID 未落实到请求和提交校验。其余三项不纳入本轮补充实施范围。

## 4. 复用与范围

### 4.1 现成能力与实践选择

优先复用以下已有能力，无需引入新的开源工作流引擎、消息 SDK 或消息队列：

- 核心 `App`、`InterventionCommandService`、固定工作流 starting lease、attempt lock、dynamic request lease 与 execution fencing。
- `RunState.execution.revision`、dynamic leaf 的 `runtime_lifecycle_revision`、完整 locator 与现有 task/run UUID。
- `RuntimeLifecycleEvent::InterventionRequested`、有界 projection queue、SQLite outbox、入站审计、重试、租约和 connection generation。
- 飞书/企微现有 typed card、`PublishedAction { index }`、回调短引用、跨端终态与 `Send / TombstoneOnly`。
- 现有 Tokio、serde、rusqlite 和平台协议隔离层；桌面设置控件继续复用项目 shadcn/ui、Tailwind 组件。

实践原则是单一事实源、显式 command、在提交点执行条件更新、可靠入队后重试和有界处理。IM 是同一命令的另一个入口，不根据自然语言、Agent 回复或按钮文字推进流程。外部协议依据沿用[远程干预设计 §14](../../产品设计文档/integration/im-remote-intervention.md#14-外部协议依据)；实施时再次核对两平台官方卡片与回调契约，不把现有回调时限视为永久平台承诺。

### 4.2 本次范围

1. 固定 Workflow/AUTO 暂停后的“继续工作流”。
2. 固定工作流当前节点已成功完成、控制流尚未推进时的“恢复工作流”。
3. AI-DYNAMIC 当前可继续 leaf 的精确远程继续，包括外层仍 Running 的情况；完成 leaf 的历史 completion reconciliation 继续使用现有 leaf continue 路径，不套用固定节点 recovery。
4. 桌面、飞书、企微共享资格、写入、幂等和状态刷新。
5. 独立通知偏好、七语言资源、投递诊断、接口回归和真实平台验收。

不增加远程启动、停止、重跑、工作流编辑、自然语言指令或“继续并发送”表单。桌面现有“继续并发送”仍保留，并使用同一源边界校验。Direct、结构化问答、权限、manual check、ErrorBlocked 和仍在自动重试的执行不通过通用继续绕过。升级前已经暂停的全部历史运行不做全量补发。

### 5.2 类型设计

以下为已实现的核心接口形状，位于 `src/app/runtime_resume.rs`：

```rust
enum RuntimeResumeKind {
    ContinueCurrentAttempt,
    RecoverCompletedAttempt,
}

enum RuntimeResumeBoundary {
    RunExecution { revision: u64 },
    DynamicLeaf { revision: u64 },
}

struct RuntimeResumeSourceIdentity {
    task_uuid: String,
    run_uuid: String,
}

struct RuntimeResumeOffer {
    locator: InterventionLocator,
    source_identity: RuntimeResumeSourceIdentity,
    kind: RuntimeResumeKind,
    boundary: RuntimeResumeBoundary,
}

enum RuntimeResumeReadiness {
    Ready,
    Busy { reason: RuntimeResumeBusyReason },
}

struct RuntimeResumeInspection {
    offer: RuntimeResumeOffer,
    readiness: RuntimeResumeReadiness,
    pause_reason: Option<PauseReason>, // 仅显示，不进入 offer/指纹
}
```

`RuntimeResumeOffer` 是可重建投影，不新增 pending 文件、Run 字段或持久化 aggregate。固定目标使用既有 Run execution revision；dynamic 使用目标 leaf 的既有 lifecycle revision，并额外复核当前 outer owner。不能只比较外层 Run revision：兄弟 leaf 的运行变化不应无故使当前暂停 leaf 的动作失效。

`source_identity` 只复制既有身份事实，不创建新的 Runtime identity。`readiness` 是当前执行准入的瞬时观察，不持久化、不进入请求身份或指纹。Busy 与不可恢复/已失效必须使用不同的 typed 分支。

`inspect` 返回 `Result<RuntimeResumeInspection, InterventionError>`；Unavailable 使用已有结构化错误容器，存储暂时不可用为 retryable，资格/身份/边界不匹配为不可用。Busy 是成功 inspection 中的独立 readiness，不经错误或取消分支结算。

已扩展现有类型：

- `InterventionRequestIdentity::RuntimeResume { source_identity, resume_kind, boundary }`：与完整 locator 一起绑定原 task/run 实例的一次源暂停；UUID 不能仅出现在 event ID 中。
- `InterventionAllowedAction::RuntimeResume { resume_kind }` 与 `InterventionAction::RuntimeResume { resume_kind }`：只接受该卡实际发布的那一种动作。
- `RuntimeInterventionKind::RuntimeResumeRequired`、`ImNotificationKind::WorkflowResume`：一类通知覆盖继续与恢复，按钮由 typed kind 决定。
- `ImResolutionOutcome` 增加已提交的 RuntimeResume 结果，携带动作种类、命令返回的提交 revision、启动/恢复结果及必要的结构化错误；未知结果复用 `ResultUnavailable`，失效复用取消/过期投影。已提交但启动失败也必须如实表示，不能仅根据动作类型生成成功结果。

无须为 connector 增加新的通用指令入口：复用 `ImSubmittedAction::PublishedAction` 还原 outbox 的允许动作。所有文本 key 集中在所属语言资源，错误使用结构化类型和参数，不在后端业务代码拼接对客文案。

### 5.3 请求身份、事件与指纹

- 固定请求的身份输入为完整 project/task/run/round/node/attempt locator、显式 `source_identity.task_uuid/run_uuid`、`RunExecution.revision` 与动作种类。
- Dynamic 请求还必须包含 outer node/attempt 与 leaf node/attempt，revision 取 leaf 生命周期。
- canonical event ID 由统一 helper 对上述 typed 输入生成有界稳定 ID；同一提交被不同发布路径观察时得到同一 ID，再次暂停因 revision 前进得到新 ID。
- 不直接复用仅由 attempt/reason 构造的旧去重 key，也不解析旧事件 ID、时间戳、标题或 Agent 文本反查边界。
- `expected_state` 仅覆盖决策语义：源 UUID、locator、源 boundary、允许动作和持久资格所需状态。不含 readiness、临时 prompt/lease、模型输出、timelineIdentity、计时、标题或布局等展示字段。
- 源 UUID 与 boundary 随暂停事实捕获，并进入事件、请求、指纹和 outbox；回调从已发布请求还原原值。迟到事件不能在投影时换用当前实体的 UUID 或更新的暂停 boundary；不一致时分别记录 `source-identity-changed` 或 `stale-boundary`。
- task UUID 以当前 Task canonical 元数据为准，须与 Run 的 `task_uuid` 一致；run UUID 取该 Run 既有 `uuid`。任一缺失或归属不一致时返回结构化 Unavailable，不在读取/投影时生成 UUID，不退回编号、路径或名称匹配。已有元数据缺失的治理不通过本功能补造身份。

## 6. 统一资格与接口

### 6.1 资格表

| 当前 canonical 状态 | 动作 |
| --- | --- |
| Workflow/AUTO 当前普通 attempt 暂停、无 outcome、允许显式继续、无 manual check/待响应交互 | ContinueCurrentAttempt；活动 prompt/冲突 lease 仅使 readiness 为 Busy |
| 当前普通 attempt 已 Completed + Success，Run 因允许恢复的原因暂停，后继尚未提交、无 manual check | RecoverCompletedAttempt |
| 当前 AI-DYNAMIC owner 下可继续的精确 leaf，leaf boundary 有效 | ContinueCurrentAttempt，沿用 dynamic continue 与 completion reconciliation；目标 leaf 的瞬时活动使 readiness 为 Busy |
| Direct、历史 attempt、已替换 outer owner、终态 Run | 无动作 |
| Permission、Elicitation、ManualCheck、ErrorBlocked、自动重试尚未结束 | 无通用动作，保留原处理入口 |

允许恢复的暂停原因沿用 `PauseReason::allows_explicit_runtime_continue`。固定 Run 必须 Paused；dynamic 不能机械套用该条件，需允许其他 leaf 正在执行时对当前暂停 leaf 发起继续。运行环境、Agent、profile 和 Git/worktree 校验属于提交前 executable preflight，不能放进列表/设置首屏的资格投影。

表中动作还要求源 UUID 完整且匹配。暂停提交后的旧 starting lease、prompt 收尾，以及同一会话短暂的 NonRuntime 聊天，不消耗这次暂停请求；readiness 恢复 Ready 后仍是原请求。Permission/Elicitation/ManualCheck/ErrorBlocked 等仍走原专用入口，不能改称 Busy 后经通用继续绕过。

### 6.2 共享服务

在核心 `src/app/` 增加职责明确的 Runtime resume 应用边界，或在既有 intervention 模块内按同一职责拆分；不创建通用 command bus：

```text
inspect_runtime_resume(locator) -> Result<RuntimeResumeInspection, InterventionError>
inspect_runtime_resume_with_state(locator, loaded_run, loaded_graph) -> Result<RuntimeResumeInspection, InterventionError>
execute_runtime_resume(offer, optional_desktop_input) -> authoritative result
```

`inspect` 统一桌面 lifecycle、远程投影和 command admission 的语义；写入口必须在 Runtime 提交锁内重新执行最终校验。`InterventionCommandService` 的 RuntimeResume 分支委托该服务；Tauri continue/recovery command 同样委托它，禁止 IM 调用外层 Tauri command。平台来源信息只进入现有审计与终态投影，不影响核心资格。

桌面 VM 保留 `continueKind` 文案契约，并从共享结果返回源 UUID、typed boundary 与独立 readiness；fixed 可复用当前 runtime revision，dynamic 必须明确它是 leaf revision。纯继续、继续并发送、完成节点恢复均提交用户看到的源身份和 boundary。公开用户入口不得保留“先读取当前身份/revision 再无条件继续”的旁路；既有内部入口按调用职责收敛，不新增旧行为 fallback。

通知资格只依赖持久的 Eligible；Busy 时仍发布并入队正常源卡，发送前复核源身份和持久资格，不因瞬时 Busy 丢弃通知。点击时以最新 admission 为准：若仍 Busy，返回可重试的忙碌结果，保留原卡动作和指纹，不自动排队执行。桌面沿用既有处理中/按钮禁用呈现。

### 6.3 条件提交与锁顺序

1. 做用户输入及不产生执行副作用的 executable preflight 检查，可先拒绝明显不匹配的源身份；会创建资源或启动执行的步骤须等第 3 步通过并受既有 fencing 保护。不持有数据库事务等待网络或 Agent。
2. 复用对应 fixed starting lease 或 dynamic request lease，取得原 Runtime 的 owner/attempt 锁。
3. 在同一提交临界区重新读取当前 task/run，逐项核对请求中的 task/run UUID、Run 的 task_uuid 归属、完整 locator、源 boundary、动作种类、生命周期、manual check/pending interaction 与目标活动状态。dynamic 同时核对父 Run UUID、outer owner 和目标 leaf revision。
4. 校验成功后才登记 runtime recovery candidate，并按既有顺序提交新的 execution 与 Running；校验失败不得先替换 candidate 再撤销。
5. 保留 continue 的启动握手和动态 lease fencing；握手后失败按原 execution identity 收敛，迟到失败不能覆盖更新的停止或新执行。
6. recovery 复用 `run_recover_completed_background` 的 revision 校验，直接计算后继，不能重新调用已完成节点的 provider；无后继时允许直接得到已完成 Run。

`inspect` 与外部执行之间加一个全局锁不能替代第 3 步。fixed 的源 revision 检查必须进入 `commit_fixed_run_continue` 的提交边界；dynamic 的检查必须进入 leaf lease/graph 提交边界，并保持当前 outer/leaf 锁序，不能在 IM 层持锁包住启动等待。

UUID 校验也在该提交边界完成，不能只依赖 event ID 去重或提交前读取；当前实体的替换/删除须与现有实体锁的保护范围一致，不能持有旧对象引用就认定它仍是当前实体。即使可读编号、locator 和 revision 全部相同，只要 task/run UUID 不同也拒绝。身份拒绝必须发生在 candidate 登记、Runtime 写入和 provider 调用之前。

| --- | --- |
| 该请求已接受，审计存在 | AlreadyApplied，使用首次已知结果，不再次启动 |
| 源 boundary 已变化、但无成功证据 | 状态已变化/结果未知，旧卡失效；不能把 revision conflict 一律包装成“已成功继续” |
| 仍是原 boundary，preflight 或初始化在提交前失败 | 结构化失败；原卡保持可重试 |
| 仍是原实体和 boundary，仅活动 prompt/冲突 lease 未结束 | Busy，可稍后重试；不写终态、不换指纹、不自动继续 |
| task/run UUID 缺失、归属不一致或已替换 | 结构化身份错误；旧源请求不可执行，不生成身份或猜测当前目标 |
| Running 已提交后启动失败，又收敛到新的暂停 revision | 旧卡不可重试新暂停；报告失败，新的 boundary 产生新卡 |
| 正在启动且回调预算将到 | 只反馈“处理中”，不写成功终态；后台继续既有执行 |
| owner、权限、binding、generation 或卡片过期校验失败 | 明确拒绝，不触发 Runtime |

复用现有结构化错误容器，优先沿用已有错误码；确需新增时以所属类型集中定义，例如 boundary stale、source identity missing/changed、runtime busy、action unavailable、launch failed。桌面前端与 `src/im/locales/` 分别本地化，不把 provider 原始错误直接作为手机文案。

共享命令结果必须区分 `NotCommitted { error, retryable }` 与 `Committed { kind, revision, result }`；后者的 result 至少区分已启动、已恢复推进、已完成与启动失败。它描述本次既有提交的返回值，不是新的持久执行状态机；处理来源只归属于实际完成条件提交的入口。提交前 Busy/失败不记录成功审计，提交后失败不退回 NotCommitted。

## 7. 暂停发布、投递与恢复边界

### 7.1 统一发布

在 canonical 暂停/可恢复事实完成持久化后，统一 helper 检查并发布现有 `InterventionRequested`，其中 request 为 RuntimeResume、kind 为 RuntimeResumeRequired。原 `RunPaused` 继续表达原有运行状态，不把 leaf 暂停伪装成外层 Run 已暂停。

必须接入的写路径包括：普通 Run stop、attempt 异常收敛、orchestrator 的暂停/完成节点恢复边界、dynamic 单 leaf 暂停及整图暂停后的相关 leaf。dynamic 只枚举本次已知变化的 leaf ID；外层和 leaf 发布不得同时为同一断点生成两个可执行请求。

发布源状态快照与 boundary 必须一致。helper 不能盲目改写状态或触发 Agent；没有可行动渠道时，subscriber 沿用轻量 target-first 快速返回。`RunPaused` 与新的语义干预事件均出现时，IM 只从后者创建本类 source delivery，避免重复。

补齐清理后的事件契约：固定启动握手/失败收敛的 starting lease 释放后、目标 prompt 收尾后、dynamic request lease 完成后，由对应 Runtime 收尾路径对本次已知 locator 调用同一检查/发布 helper。纯 Drop 只移除 lease 不足以保证该契约，应在拥有任务上下文的 finalize 路径安排释放后的调用；原 Busy 请求因此重新获得观察机会，包括首次未形成 outbox source 的路径。NonRuntime prompt 结束也走同一已知目标的唤醒入口。

上述收尾调用携带任务已捕获的源 UUID、boundary、kind，先与当前事实核对再发布；新暂停、实体替换或 owner 更换后不重发旧源。仍有效时使用相同 canonical event ID 和原暂停时间，多个完成信号只产生一份 delivery。首次暂停发布不能等待清理，也不能因 Busy 跳过；收尾发布复用现有生命周期订阅/合并唤醒，不依赖只看已入库卡的 settlement，不增加每请求计时器、任意延迟或平行 pending 集合。

### 7.2 Outbox

复用现有 Intervention payload、唯一约束、delivery ID、outbox 额度、发送 lease、重试和 worker。源卡最长有效期沿用现有干预 24 小时上限，并以源暂停时间计算，replay 不延长 TTL；源 boundary 失效时提前关闭。继续执行本身不受卡片 TTL 改变，桌面仍按最新资格操作。

离线但客户端仍运行时先入 outbox，连接恢复后重试；发送前再次检查源请求仍有效。已处理、过期、被新暂停替换的源消息不能因发送失败或租约恢复再次发成可操作卡。先记录终态的 `TombstoneOnly` 继续拦截迟到源投影。

可靠重试的起点是 source delivery 已持久化。当前文件状态提交、内存 lifecycle queue 与 SQLite outbox 之间不是一个事务；本次不增加新消息中间件或全历史回放，也不宣称该跨存储窗口零丢失。投影队列满、关闭和入库失败必须产生现有诊断；重启后继续投递已入库记录，Runtime recovery 已知 locator 的状态修复完成后按同一 helper 发布。升级前既有暂停和崩溃于入库前的全部历史暂停不承诺自动补发；若要求从 canonical commit 起严格不漏，需另行设计持久发布意图，而不能以定时全目录扫描替代。

### 7.3 跨端结算与幂等

- 桌面、飞书、企微同一源 boundary 竞争同一 Runtime 提交条件，只允许一次有效执行；两个渠道各自的审计不能代替该条件。
- 只有确定 Accepted 的赢家记录处理来源；其余入口读取已知结果或显示状态已变化，不能覆盖来源。
- Runtime 先提交执行、IM 后写审计的窗口中若崩溃，重放因旧 boundary 不匹配而不能启动第二次。找不到成功审计时使用 ResultUnavailable，不猜测是哪一端继续。
- 扩展现有 settlement 查询及合并唤醒机制：原源身份与持久资格仍有效则保持 Pending，包括 readiness 为 Busy 的情况；已知动作接受则投影已处理；源 UUID、owner、boundary、终态或过期变化则关闭旧请求。Busy、可重试 preflight 失败都不能生成终态 tombstone。复用已有 30 秒校准兜底，不新增轮询任务；只检查现有 outbox 当前未结算源卡，并按请求身份去重。它不承担首次通知发现职责。
- 立即成功的恢复操作可能已经把 Run 推进到终态。结果以命令返回的最新事实为准，不能强行回显 Running，也不能宣称“请求接受”等于整条工作流完成。

## 8. 手机与桌面交互

### 8.1 卡片内容

标题按 kind 显示“工作流已暂停”或“工作流等待恢复”，内容仅展示工作空间、任务、节点/leaf、暂停原因和可执行操作。未知原因显示中性暂停信息，不把 `process-interrupted` 翻译为“用户停止”。不展示大段 thought、完整工具输出、系统路径或恢复实现说明。

初始卡片只发布一个执行按钮：“继续工作流”或“恢复工作流”。不增加默认勾选的自动继续、拒绝即终止、停止或重跑动作。用户忽略消息时流程保持当前状态。暂停清理期间也可收到该卡；点击若仍 Busy，提示稍后重试并保留按钮。点击后的平台 toast 或临时回包显示“处理中”；有权威执行结果后显示已继续、已恢复、已完成或结构化失败原因。

### 8.2 平台投影

- 飞书复用 typed action button、`PublishedAction` 和原卡更新链路；成功后关闭原卡动作。慢执行不得占住回调确认，按当前连接器预算先回处理中，最终通过 outbox 更新。
- 企微复用已存在的 `button_interaction` typed wire 路径与 `<delivery_id>@<request_nonce>` 短引用，只发布一个动作。详情仍沿用“详情 ACK 后发卡”的上下文策略；同一回调内终态保持原 card type/task/key，不能假造平台消息 ID。
- 企微只在当前可用的 CallbackOnly 窗口内更新原卡；执行超出窗口、桌面或另一渠道处理时使用只读结果通知。原卡重复可点仍由入站与 Runtime 条件更新阻止副作用。
- 飞书已有 2.5 秒回调等待机制；企微的 5 秒是现有文档中的协议目标，当前实现尚无覆盖领域处理的端到端期限，不能把处理结束后才开始的 15 秒请求网络超时当作该保障。两平台窗口、ACK 含义和一次回调允许的响应次数在实施期按官方协议及真实手机复核；本文没有新增真实平台验证结论。

### 8.2.1 企微回调期限与实际回执

1. Connector 接收回调时以单调时钟捕获 arrival/deadline，保留在 connector-owned response context；排队、blocking pool 调度、领域处理和网络发送均消耗同一回调窗口。响应调度预留安全余量，窗口及余量集中定义，不在各层重置计时。平台回调窗口和通用请求传输超时分别管理。
2. `run_inbound_action` 中领域任务与限时回包等待分离。预算内有最终结果则尝试终态更新；接近截止仍无结果时，仅在协议允许时回应处理中。超过期限不再尝试回调终态替换，领域任务继续运行；超时不取消已获准的 Runtime 操作，也不重新提交它。
3. 不预设可以先回应处理中、再用同一次回调替换最终卡。若本次响应机会已使用，最终结果直接走 outbox；若平台没有可确认的终态替换能力，也走相同降级路径。

Connector 的 `respond_to_action` 已从只返回 `Result<()>` 扩展为 typed 实际回执，语义如下；错误也归一为未确认，不由渠道能力推断成功：

```text
FinalCardUpdated { source_delivery_id, action_id, generation }
FeedbackOnly { kind: Processing | RetryableFailure }
Unconfirmed { reason: Expired | Failed | Unknown }
```

`FinalCardUpdated` 只表示平台在有效窗口内确认了本次源卡的最终结果替换，须绑定原 source delivery、既有入站 action ID 和 connection generation。仅发送成功、写入 socket、处理中 ACK、其他动作的 ACK 或旧 generation 响应都不足以产生该回执；平台若不能提供可验证确认，返回 Unknown。该回执是传输结果，不是新的 Runtime 状态。

`FeedbackOnly` 表示已确认的提示反馈，不表示源请求已结算。Processing 不能替代最终结果；RetryableFailure 仅在本次可重试失败提示得到确认时返回，否则为 Unconfirmed，并走只读反馈补投。

### 8.2.2 最终反馈与结算顺序

| 领域结果与回调事实 | 必须处理 |
| --- | --- |
| 已知接受/最终失效，且点击源卡有匹配的 FinalCardUpdated | 该 CallbackOnly 源卡可写 TombstoneOnly；其他已显示渠道按原规则确认 |
| 已知接受/最终失效，但仅 Processing、超时、失败或未知 ACK | 经现有 outbox 持久化并发送最终只读结果；不能仅因点击来自企微就省略通知 |
| Busy、preflight 或初始化在提交前失败，源请求仍有效 | 反馈本次动作失败并保留原卡可重试；不生成 InterventionResolution，不关闭源请求 |
| Running 已提交后启动失败并产生新暂停 | 旧请求按原提交事实结算，最终反馈明确启动失败；新 boundary 另发请求，不把旧卡重新开放为新暂停 |

提交前失败在窗口内返回可重试提示；若未确认最终失败提示已经可见，使用现有 outbox 的只读反馈路径。拟增加 typed `ActionFeedback` payload，绑定 `source_delivery_id` 与既有 `action_id`，只携带结构化错误、参数和 retryable 信息；其确定性投递 ID 按源投递及 action ID 生成，不新增表或队列。同一回调重放只生成一份反馈，新点击是新的动作；该 payload 不参与源请求终态唯一约束，也不借用“已处理”结果取消重试。只向仍通过 binding/generation 授权校验的原私聊反馈，不把鉴权失败的回调用于外发。

已提交动作的最终反馈以命令的权威结果为准，不能从“用户点了继续”直接合成成功；continue/recovery 的已接受、启动失败和立即完成都要保留区别。在既有 `im_inbound_actions` 增加 `result_payload_json`，保存 RuntimeResume 的 typed 动作结果：动作种类、是否已提交、提交 revision、启动/恢复结果及结构化错误；不复制完整 Run/Node 状态。通过授权校验的可重试失败也按既有 action ID 记录该结果，同 callback 重放只重现首次结果，新 callback 才能重试。相应序列化变更纳入 §9 的 schema gate，不增加 accepted command 表。

入站任务是其已提交结果的发布方；通用 settlement 不抢先把已有 Accepted 审计解释为取消或结果未知。在既有动作锁/任务上下文中增加以 canonical source event ID 为 key 的临时投影 guard，覆盖领域提交、审计、回执判断至最终入队；桌面等显式提交入口也遵守同源结果发布顺序。settlement 对被占用的源只合并完成唤醒，其他源正常校准；同源重复点击读取已有结果或回应处理中，不排队第二次领域执行。guard 使用作用域释放，不持有 Runtime 锁或 SQLite 事务跨网络等待，不新增持久命令状态或独立 pending 队列。

最终投影显式接收实际回执，只有匹配确认才允许省略发送。无活跃任务、重启或回执无法确认时采用保守 Send；若 Send 已持久化，迟到 ACK 不把它改成 TombstoneOnly。极端 ACK 不确定或结算竞争时允许重复呈现确认，不能漏掉最终反馈或再次执行 Runtime；赢家来源只由已知接受事实确定。

### 8.3 偏好与桌面刷新

每渠道增加“工作流继续请求”通知偏好（`workflow_resume`），默认开启，放入现有“需要你处理”组，统一控制继续与恢复。“继续请求”表达需要用户确认流程继续推进，卡片按钮仍按实际动作显示“继续工作流”或“恢复工作流”；不挤占 `manual_check`、`run_failure` 或 `acp_turn_finished`。总开关与其他逐类开关仍各自生效，关闭该项只影响提醒，不更改暂停状态。

桌面复用现有 continue/recovery 按钮位置、文案与中间态。IM 接受后走与桌面相同的 session/lifecycle 更新链路，以完整 locator、revision 局部收敛当前 composer、节点与侧栏；不重新加载全部会话/历史。普通发送和 Enter 保持 NonRuntime，不因手机卡片出现而变成继续。

`web/src/locales/` 与 `src/im/locales/` 同步维护 zh-CN、zh-TW、en、ja-JP、ko-KR、pt-BR、es。复用现有隐藏 RuntimeResume prompt，不新增或修改 prompt 正文；若实施发现必须改正文，先完整读取 `prompt-authoring.md` 并按提示词语言规则另行维护。

## 10. 可观测性与可靠性限制

按现有诊断边界记录事件 ID、完整业务 locator、动作、源/当前 revision、源 UUID 核验结果、渠道、阶段与稳定 reason code。阶段覆盖 eligibility、projection、outbox、send、callback、admission、launch、resolution；reason 区分无资格、瞬时 Busy、身份缺失/替换、偏好关闭、未绑定、旧边界、队列饱和、入库失败、平台发送失败和启动失败。回调另记录 arrival 到响应的分段耗时、剩余预算与 typed 回执类别，能够区分领域慢、响应失败及未确认更新，不输出平台原始响应正文。

跳过结果应包含 bounded 结构化分类，不能只有一个 skipped 总数；不为每条流式 chunk 写通知诊断。正常关闭/无渠道不写持续 warning，无目标时不额外读 workspace/SQLite。日志不包含凭据、平台用户 ID、问题答案、完整 prompt 或工具原始内容。

客户端退出、电脑休眠或断网时不保证实时操作；恢复依赖桌面进程及本机执行环境。平台消息去重与回调预算仍有其限制，不宣称消息恰好发送一次。是否触发本次现场中断仍需客户端控制日志进一步确认，与补齐远程操作能力分别跟踪。

## 13. 性能影响评审

### 13.1 规模与关键路径

- 渠道最多 2 个；本类源卡每个暂停边界每渠道最多 1 条，结算另复用既有终态记录。ActionFeedback 每个已授权 action ID 最多一份，沿用现有 outbox 配额和审计保留期，重复回调不放大记录数。
- 现有 projection queue 容量 256、active outbox 上限 1000、due claim 单批最多 32；本方案不提高这些上限，不增加连接或 worker。
- 固定目标检查只读当前 Task/Run/Node、轻量 ACP/pending 元数据；UUID 为固定数量比较，复杂度不随历史消息数增长。禁止构建完整 session VM 或读取 raw/timeline 正文。
- Dynamic 若现有 canonical graph 操作需要加载当前图，其成本按该图节点数 `G` 计为 O(G)，不声称 O(1)；优先复用写路径已加载的图及 changed leaf IDs，不因每渠道重复加载图，不跨历史图扫描。
- 单次投影 O(C)，C≤2；现有 settlement 校准只处理有上限的 open outbox sources，按请求去重，每个目标读取一次，不新增全历史轮询。
- 网络、执行 preflight 和启动等待不占用数据库事务、事件线程或领域锁；短锁只覆盖必要事实读取/校验/提交。
- readiness 不持久化或高频轮询；清理后的重检只针对本任务已知 locator，沿用稳定 ID 去重和现有有界投影队列。回调期限等待使用异步计时，不阻塞 connector 事件循环；回执上下文随响应窗口结束释放，源投影 guard 随领域任务完成及结果入队释放，不能因回调超时提前释放。guard 复用动作锁的作用域清理，不新增无界注册表。

### 13.2 验收目标

新增路径的基线测量在实施前记录，不能预填耗时结论。用相同目标分别构造 0 与 10 万条历史消息、1 与 100 个当前 dynamic leaf 的夹具，验收：

1. 固定恢复资格/投影的 timeline/raw 正文读取次数均为 0，历史规模增大不增加目标读取次数。
2. 两渠道共享一次 canonical inspect；单个 leaf 变化只投影该 leaf，兄弟变化不触发所有暂停卡重建。
3. 当前 graph 每次投影至多一次加载，不按渠道产生 N+1；大图与多待处理卡的耗时/读取次数须记录。
4. outbox 和队列不突破现有上限，空目标不做新 I/O；在已有 5 万过期记录和少量有效记录下仍使用 open-intervention 局部索引，不遍历过期历史。
5. session/lifecycle 更新只刷新对应 locator；无全局 Loading、全量 sidebar/history 重取或新增高频 Context 订阅。
6. 用可控时钟验证企微回包路径各段等待累计不越过回调预算，超窗领域任务仍按既有启动握手完成；清理多次触发不增加源 delivery 数，不增加历史扫描或每请求定时器。记录新增 Task 摘要读取、审计结果写入及回调耗时，确认网络等待期间不持有领域锁或 SQLite 事务。

若实测显示 graph 或校准读取超出预算，先收紧投影字段、共享同批读取和变化范围，再决定是否需要索引；不提前新增缓存、并行队列或图副本。未改变流式 Markdown/布局算法，无需为了形式新增相关 benchmark。

## 14. 过度设计评审与风险

本方案复用既有 canonical identity、revision、lease、outbox、审计和卡片；没有新增工作流状态、accepted command 表、后台队列、通用命令总线或依赖。typed boundary 与既有 UUID 的请求快照共同表达“原实体的哪一次暂停”，解决同编号实体替换及旧源提交校验，不创建第二套 canonical identity。readiness 与实际回执只描述瞬时准入/传输事实，不成为业务状态机；清理后重检复用既有任务生命周期。临时投影 guard 只序列化同源回执/结算顺序，解决终态抢写，不代替 Runtime admission。持久化增量限于通知偏好、请求中的既有源 UUID、必要的动作审计结果和现有 outbox 的反馈 payload，schema gate 统一隔离新读取能力。

需要实施评审重点确认：

| 风险 | 控制方式 |
| --- | --- |
| 只订阅 RunPaused 导致 dynamic leaf 漏通知 | 从持久化 leaf 变化发布语义干预，保持 outer/leaf 区分 |
| 仅投影时校验 revision，执行时恢复了新暂停 | 在原 Runtime 提交锁/lease 内检查 typed source boundary |
| 暂停先于 lease/prompt 清理，Busy 被当成无请求 | 分离持久资格与 readiness，Busy 正常通知并保持 Pending，收尾按原身份重检/去重 |
| 企微超窗或更新失败却省略结果通知 | arrival 起算的期限与领域任务分离；只有匹配终态回执允许 TombstoneOnly，其余经 outbox 反馈 |
| UUID 只参与去重，旧卡仍能命中同编号新实体 | UUID 进入请求/指纹和提交参数，在原 Runtime 锁内核对当前 Task/Run 归属 |
| 将 stale 当成成功，或将已接受当成整个工作流完成 | 细分已知接受、结果未知、状态失效与最新 Run 结果 |
| 跨文件/SQLite 崩溃窗口被过度承诺 | 明确 outbox 持久化后的可靠边界，不以扫描或新状态掩盖 |
| 完成节点恢复、dynamic completion 与普通继续混用 | 共享语义判断、分派到各自既有执行入口，接口回归固定 |
| 文档把局部验证误写成完整验收 | 同步记录实现范围、定向验证、独立评审/全量回归和真实平台待办 |

文档阶段复核结论：新增类型和偏好与本次跨端继续/恢复需求相匹配；不扩展远程控制台，也不重做 Runtime。实现完成时必须再次按实际代码和数据规模复核性能、复杂度及剩余风险。

## 15. 文档阶段与实施记录

文档阶段：先交付本技术方案及产品设计、主实施计划路由，并补充前三项自评审的处理流程与 R16–R25 场景。该阶段没有修改实现或执行验收；以下是用户随后批准实施后的记录。

### 15.1 实现范围与接口差异

- 新增共享 `runtime_resume` 应用边界，桌面继续/继续并发送/恢复和 IM 都提交所见的 offer。固定提交与 dynamic 的 reserve、outer 提交、leaf 应用沿用原锁/lease 核对 UUID、owner 和 typed boundary，不补造 UUID。纯显示为暂停、canonical leaf 尚未提交暂停的旧图不开放继续；不通过 ACP cancelled 或父状态反推新的 leaf boundary。
- Busy 不进入指纹，也不使源请求结算；暂停及 prompt/启动清理后按原 offer 重检。Dynamic 在兄弟仍运行时发布精确 leaf 卡，VM 与发布复用已加载 graph。当前 pending interaction 只点查 snapshot 标识的交互文件，不调用可能读取历史分支的 settlement helper。
- 命令使用作用域内 `RuntimeResumeAdmission` 接收原提交点的明确证据，不根据任意 revision 变化猜成功。动态结果的 revision 取 leaf；已提交后失败与提交前失败分别投影。该对象不持久化、不构成另一套业务状态。
- 企微以 arrival 起算 5 秒窗口，connector 预留 500 ms，Runtime 在剩余预算内另留 300 ms 调度处理中回复；只发送一次回包。只有匹配真实 ACK 才返回 `FinalCardUpdated`；未确认的终态走 outbox。Busy/preflight 的失败提示已确认时省略额外反馈，否则按源 delivery/action 去重补投 `ActionFeedback`，不关闭原请求。
- 复用临时同源投影 guard 串行化领域处理、审计、回执与结算入队；不同源独立，释放后清理 registry。新增 bounded 跳过原因和回调剩余预算/耗时/回执诊断，不输出凭据、答案或平台响应正文。
- 卡片按 Continue/Recovery 区分标题，从同一次 canonical inspection 提取 Run/leaf 的暂停原因，仅以 typed 投影传给 IM 文案选择，不加入请求身份或增加图读取。企微单按钮卡直接展示工作空间、任务和节点，并在副标题保留暂停原因及操作说明；不沿用仅适合详情联动卡的上下文隐藏规则。
- Settings 14、IM component 7 的迁移已实现；七语言新增“工作流继续请求”与动作/结果文案，没有新增运行时依赖、表、Runtime 持久字段、队列或提示词正文；桌面测试仅显式引用工作区已有的 async-trait，也没有修改共享规则。

### 16.1 P1：暂停发布与清理解耦

目标：canonical pause 状态可靠写入后，立即发布暂停状态和可操作请求，不等待 prompt 取消、snapshot 写入、旧 lease stop 或子 Run 清理；清理失败只记录诊断，不阻断通知。

实现约束：

1. 将组合入口 `publish_committed_attempt_pause` 拆成状态发布与请求发布两个内部职责：Run 状态只发布一次 `RunPaused`，请求发布从当前 canonical Run/Node/Graph 生成 RuntimeResume。
2. 固定 Run 在 Run/Round/Node 写盘并释放 attempt lock 后立即发布，不等待 `interrupt_attempt_artifacts_best_effort`。
3. Dynamic 必须先持久化 graph/leaf 的 paused 状态；图状态提交并释放 graph lock 后立即发布 leaf 请求，再执行 prompt 取消、旧 lease stop 和子 Run 清理。不得在 canonical graph 状态尚未提交时伪造 leaf 请求。
   dynamic run/node/coordination 为派生投影，放在发布之后 best-effort 刷新；刷新时在原 graph lock 内重读当前图，避免迟到的旧暂停投影覆盖新恢复事实。投影失败只记诊断，不使已提交暂停返回失败，也不吞通知。
4. `stop_dynamic_resume_target`、prompt 取消和子 Run 暂停均为 best-effort 后置清理。清理错误写入结构化诊断，但不得使用 `?` 在发布前提前返回。
5. 清理结束后使用同一 canonical event ID 重检并重投；已有 outbox 唯一约束负责去重。新暂停产生新 boundary/event ID；迟到重投通过 `publish_runtime_resume_offer` 的当前状态校验自然失效。
6. 不新增持久发布意图、历史扫描或补发队列。跨存储窗口仍按 §7.2 的既有边界处理。
7. 提前发布不能让迟到清理误伤新恢复的执行。提交锁内捕获旧 request ID、provider control 和 ACP lifecycle header；锁外只取消所捕获的 control，由其原 executor 发送取消与结算 interaction，snapshot 在既有 metadata lock 内按原 header CAS 结算。Dynamic 旧 lease 仅按捕获的 request ID 撤销，不按当前 attempt 广泛匹配；整体暂停的 graph 后置提交也核对原 Run identity/revision。捕获结果仅属于本次调用，不持久化、不作为资格事实源。

验收：

- 使用 graph lock 或可控 cleanup barrier 卡住清理，断言 `RunPaused` 与固定 Resume 请求在清理释放前已发布。
- 模拟 `stop_dynamic_resume_target` 失败，断言 canonical pause 已持久化时仍产生通知。
- 将 coordination 投影路径替换为目录，断言 canonical graph 已暂停后仍返回成功并发布 leaf 请求；不能把辅助投影的写入失败当成 canonical 提交失败。
- 清理完成后同源重投每渠道仍只有一条 delivery。
- 固定 Run、单 leaf dynamic、整体 dynamic pause 三条路径均覆盖；重跑 R16、R18 和既有暂停发布测试。
